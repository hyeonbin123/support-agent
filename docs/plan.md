# 개발 계획 (2026-09-19, 개발 시작 전)

## 목표
한국어 고객센터 업무를 도구 호출로 처리하는 LLM 상담 에이전트를 만들고, **미리 정한 규칙으로 얼마나 믿을 만한지를 측정**한다. "데모에서 한 번 됐다"에서 끝내지 않고, 같은 과제를 여러 번 시켰을 때 몇 번 성공하는지, 규정을 어기는 일이 얼마나 있는지, 무엇을 넣으면 얼마나 나아지는지를 수치로 남긴다.

## 측정으로 답할 질문
1. 로컬에서 도는 7~14B 모델은 한국어 상담 과제를 얼마나 끝까지 처리하는가. 한 번 시켰을 때의 성공률(pass^1)과 k번 모두 성공할 비율(pass^k)은 얼마나 차이 나는가
2. 어디서 실패하는가: 본인 확인 누락, 규정 위반(안 되는 환불을 해 줌), 잘못된 인자, 고객 확인 없이 실행, 중간에 멈춤
3. 규정을 프롬프트에만 적는 것과, 코드로 검증할 수 있는 규정을 도구 안에서 막고 오류로 돌려주는 것은 성공률과 위반 수에서 얼마나 다른가
4. 실행 전에 생각을 적게 하는 단계(think 도구)와, 부작용 있는 처리 전에 고객 확인을 강제하는 절차는 효과가 있는가
5. 모델 크기와 세대에 따라 얼마나 달라지는가. 지연 시간까지 보면 어느 쪽이 나은가

## 도메인: 가상의 온라인 쇼핑몰 고객센터
- **DB**: 고객, 상품, 주문, 주문 상품, 결제, 배송, 반품·교환 요청, 쿠폰, 상담 티켓
- **규정 문서** (한국어, 1~2쪽 분량): 본인 확인 방법, 주문 취소가 가능한 상태, 반품 기한(수령 후 7일), 교환 조건, 환불 수단, 보상 쿠폰 한도, 상담원 이관 조건, 부작용 있는 처리 전 고객 확인
- 데이터는 모두 생성한다 (seed 고정). 실제 회사나 개인의 데이터는 쓰지 않는다

### 도구 (약 12개)

| 구분 | 도구 | 비고 |
|---|---|---|
| 읽기 | 고객 찾기(전화번호·이메일), 고객 정보, 주문 목록, 주문 상세, 상품 정보, 배송 조회 | 본인 확인 뒤에만 고객 정보를 돌려줌 (가드 조건) |
| 쓰기 | 주문 취소, 반품 접수, 교환 접수, 배송지 변경, 보상 쿠폰 발급, 상담 티켓 생성 | 부작용 있음. 실행 전 고객 확인, 일부는 사람 승인 |
| 기타 | 상담원 이관, think(생각 적기) | think는 실험 후보 |

도구 하나는 "입력 스키마(pydantic) + 함수(DB 세션, 인자) → 결과"로 정의한다. 같은 정의에서 LLM용 JSON Schema와 MCP 도구 정의를 함께 만든다.

## 평가 방식
τ-bench([논문](https://arxiv.org/abs/2406.12045), [τ²-bench](https://github.com/sierra-research/tau2-bench))의 방식을 따른다. 코드와 데이터는 가져오지 않고, 도메인·규정·과제를 한국어로 새로 만든다.

- **과제** = 고객 시나리오(누구이고, 무엇을 원하고, 어떤 정보를 알고 있는지) + 정답 동작(실행돼야 하는 쓰기 도구 호출 목록) + 고객에게 꼭 전달해야 하는 값(예: 환불 금액)
- **판정** (둘 다 만족해야 성공. LLM 판정은 쓰지 않는다)
  1. 대화가 끝난 뒤의 DB 상태가 "새 DB에 정답 동작만 실행한 상태"와 같다
  2. 꼭 전달해야 하는 값이 에이전트의 말에 들어 있다
- **과제 유형**: 조회형(DB 변화 없음), 처리형, 거절형(규정상 안 되는 요청. DB가 그대로여야 함), 복합형(동작 여러 개)
- **과제 수**: 개발용 약 25개, 시험용 약 40개. 개발용으로 프롬프트와 가드를 고치고, 시험용은 단계가 끝날 때 고른 후보만 한 번 잰다. 확정 수와 유형별 비율은 재기 전에 `experiments.md`에 적는다
- **반복**: 과제마다 4번. pass^k는 과제마다 n번 중 c번 성공했을 때 C(c,k)/C(n,k)의 평균 (k=1~4)
- **정답 동작 자동 검증**: 모든 과제의 정답 동작이 새 DB에서 오류 없이 실행되고, 거절형은 해당 쓰기 도구가 규정 검증에서 실제로 막히는지 테스트로 확인한다
- **사용자 시뮬레이터**: 고객 역할을 하는 LLM. 모든 후보에 같은 모델과 같은 프롬프트를 쓴다
  - 시뮬레이터 점검: 에피소드 20개를 무작위로 뽑아 사람이 읽고, 시나리오에 없는 정보를 지어냈는지, 목표를 일찍 포기했는지, 상담원 역할을 대신했는지 센다. 비율을 결과와 함께 보고한다
- **보조 지표**: 규정 위반 수(정답에 없는 쓰기 도구가 실행된 횟수), 도구 호출 형식 오류율, 평균 턴 수, 에피소드당 시간과 토큰
- **리포트**: 에피소드마다 대화 전체, 도구 호출, 최종 DB 덤프, 판정을 JSONL로 `reports/`에 남겨 수치를 다시 계산할 수 있게 한다

## 실험 후보 (초안. 재기 전에 `experiments.md`에 확정)

| 축 | 후보 |
|---|---|
| 규정 적용 | P0 프롬프트에만 적음 / P1 코드로 검증 가능한 규정은 도구 안에서 막고 오류 메시지를 돌려줌 |
| 추론 절차 | R0 바로 도구 호출 / R1 think 도구 / R2 쓰기 도구 전 고객 확인을 루프에서 강제 |
| 모델 | qwen2.5 7B(기준) / qwen2.5 14B / 같은 크기의 새 세대 모델(예: qwen3 8B) / 한국어 특화 공개 모델 1개(라이선스와 도구 호출 지원을 확인한 뒤) |
| 참고치(선택) | API 모델 하나를 상한 참고치로 |

모든 조합을 재지 않는다. 기준(P0·R0·7B)에서 한 축씩 바꿔 개발용 과제로 고르고, 고른 구성과 기준만 시험용으로 잰다.

## 구조

```
평가 실행기 ──> 에피소드 ──> 에이전트 루프 ──> ChatProvider (Ollama / OpenAI 호환 / Anthropic)
                  │               │
                  │               └──> 도구 등록부 ──> 도메인 도구 (SQLAlchemy 세션)
                  └──> 사용자 시뮬레이터(LLM)                  │
                                              SQLite 메모리 DB(평가) / PostgreSQL(서비스)

서비스: FastAPI (스트리밍 채팅, 승인 대기열, 감사 로그) ──> 같은 에이전트 루프, 같은 도구
MCP 서버 ──> 같은 도구 등록부
```

- 에이전트 루프는 프레임워크 없이 직접 구현한다. 가드, 사람 승인, 추적 로그를 루프 안에 넣어야 하고, 분량이 작다
- 평가는 에피소드마다 seed DB를 메모리 SQLite로 복사해 쓴다 (격리, 빠름, 최종 상태 비교가 쉬움). 서비스는 같은 도구 코드를 PostgreSQL 위에서 돌린다
- GPU 없이 도는 테스트: 정해진 도구 호출을 재생하는 `ScriptedProvider`로 루프, 환경, 판정을 결정적으로 테스트한다

## 알고 시작하는 위험
- **낮은 성공률**: 공개 벤치마크에서도 작은 모델의 성공률은 낮다. 과제를 60여 개 만들기 전에 0단계에서 과제 5개로 먼저 돌려 보고, 조회형처럼 쉬운 과제를 섞어 차이를 잴 수 있는 범위를 확보한다
- **시뮬레이터 잡음**: 고객 역할 LLM이 정보를 지어내거나 일찍 포기하면 에이전트 잘못이 아닌 실패가 섞인다. 시뮬레이터를 고정하고, 점검 비율을 보고하고, 한 번의 결과가 아니라 pass^k로 본다
- **시험용 과제 오염**: 프롬프트를 고치면서 시험용 과제를 보면 수치가 부풀려진다. 개발용과 시험용을 나누고, 시험용은 단계마다 한 번만 잰다
- **GPU 한 장**: 11GB라 에이전트 모델과 시뮬레이터 모델을 함께 올리기 빠듯하다. 모델을 바꿔 올리면 느리므로(디스크에서 다시 읽음) 한 실행 안에서 모델이 바뀌지 않게 구성한다. 구성은 0단계에서 에피소드당 시간을 재서 정한다
- **범위**: 4단계(MCP)와 5단계(음성)는 앞 단계가 끝난 뒤에 한다. 5단계는 선택이다
- **직접 만든 과제의 한계**: 과제와 규정을 만든 쪽이 에이전트도 만든다. 실제 고객 대화와 다르다는 점을 한계로 적는다

| 5. 음성 연결 (선택) | 음성 인식과 음성 합성을 앞뒤에 붙인 음성 상담, 음성 인식 오류가 성공률에 주는 영향 측정 | 규칙대로 판정 |
| 6. 정리 | README 결과표, 한계, 다시 재는 방법 | 새로 클론해서 README대로 측정이 재현됨 |

각 단계의 후보와 판정 규칙은 그 단계를 재기 전에 `experiments.md`에 적고 커밋한다.
