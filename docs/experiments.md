# 측정 규칙과 결과

규칙은 재기 전에 적고 커밋한다. 결과는 같은 절 아래에 덧붙인다. 규칙을 바꾸면 바꾼 시점과 이유를 남긴다.

## 공통 규칙 (2026-09-19, 측정 전)

### 판정
- 성공 = (1) 에피소드가 끝난 DB 덤프가 "새 복사본에 정답 동작만 실행한 덤프"와 같고 (2) 꼭 전달해야 하는 값이 고객에게 전달된 상담원 발화에 있다. LLM 판정은 쓰지 않는다. 원 τ-bench 논문의 방식(행동 결과 × 전달 정보)이다
- 비교에서 빼는 컬럼은 `db.IGNORED_COLUMNS`뿐이다: 티켓 본문, 이관 요약, 이관 사유, 이관 행의 고객 번호 (규정이 본인 확인 전후 어느 쪽의 이관도 허용하므로)
- 성공 조건에 "정답에 없는 쓰기가 0건"은 넣지 않는다 (τ-bench와 같다. 바꿨다가 되돌린 쓰기는 DB가 같으면 성공이다). 대신 성공했지만 정답에 없는 쓰기가 있었던 건수를 함께 보고한다
- 전달 값 검사: 숫자는 숫자 사이의 쉼표만 지운 뒤 앞뒤가 숫자·영문자·`-`·`.`이 아닌 위치에서 찾는다. 날짜는 월·일이 같고 연도가 없거나 같으면 일치. 글자는 NFKC·소문자·공백 제거 뒤 부분 문자열. 한글 수 표기("3만 2천 원")는 인식하지 않는다
- 고객의 종료 토큰은 `### stop ###`처럼 조금 다르게 써도 인정한다. 토큰과 함께 온 말("네, 진행해 주세요 ###STOP###")은 버리지 않고 에이전트에게 전달해 한 번 답하게 한 뒤 끝낸다. 시뮬레이터의 버릇이 에이전트의 실패로 세어지지 않게 하기 위해서다
- 판정하는 종료는 고객의 종료(`user_stop`), 시나리오 밖(`out_of_scope`), 이관(`handoff`), 고객 턴 한도(`max_user_turns`)다. 에이전트 쪽 한도 초과(LLM 호출, 도구 오류, 컨텍스트)와 형식 오류 종료는 실패로 센다. 고객 턴 한도는 2026-09-19에 판정 대상으로 옮겼다: 시뮬레이터를 고친 뒤 기준선에서 일이 끝났는데도 시뮬레이터가 종료 토큰을 내지 못해 20턴을 채운 에피소드가 3개 있었다. 대화를 끝내는 것은 시뮬레이터의 몫이고, 에이전트가 시간을 끌어 얻는 것은 없다. 분석 도구는 기록된 판정 요소(DB 일치, 전달 값, 종료 사유)로 성공을 다시 계산한다 제공자 오류, 시뮬레이터의 빈 응답, 도구 코드의 버그는 `infra_error`로 기록하고 분모에서 뺀다. 공식 실행에서 `infra_error`가 나오면 건수를 결과에 적는다

### 에이전트 루프
- 텍스트와 도구 호출이 함께 오면 도구 호출을 따르고 텍스트는 고객에게 보내지 않는다 (τ-bench v1과 같은 관대한 쪽)
- 도구 호출이 여러 개면 첫 번째만 실행한다
- 형식 오류(빈 응답, 본문에 샌 도구 호출, 길이 제한으로 잘림)는 고객에게 보내지 않고, 하니스 안내문을 넣어 한 턴에 2번까지 다시 시킨다. 넘으면 실패. 본문에 샌 도구 호출은 찾아내기만 하고(태그, 또는 본문 속 `name`+`arguments` JSON) 구제 실행하지 않는다. 형식 오류 수와 재시도 수를 결과와 함께 보고한다
- 한도: 에이전트 LLM 호출 30, 고객 턴 20, 도구 오류 10. 프롬프트가 `num_ctx`의 95%를 넘으면 종료
- 본인 확인은 실험 축이 아니다. 모든 조건에서 도구가 막고, 막힌 횟수를 센다

### 도구와 규정
- 읽기 도구는 사실만 돌려준다. "반품 가능 여부"나 "반품 기한" 같은 계산된 판단은 주지 않는다 (주면 P0와 P1의 차이를 도구 출력이 메운다)
- 도구 오류 메시지에는 이유만 적고 다음 행동 힌트를 넣지 않는다
- P0와 P1의 시스템 프롬프트와 규정 문서는 같다. 다른 것은 도구의 규정 검사 동작뿐이다
- 정답 재실행과 과제 검증은 항상 P1로 돌린다

### 과제
- 과제는 `seed.py`의 고정 행만 참조한다. 과제의 `now`는 seed의 모든 시각보다 뒤다 (쿠폰 만료 시각은 예외)
- 쓰기 인자를 결정하는 모든 선택(사유, 대상 줄, 교환할 옵션, 주소)은 시나리오의 `known`에 적는다. 시뮬레이터가 고를 여지를 두지 않는다
- 전달 값은 도구 결과에서만 알 수 있는 값으로 하고, 시나리오와 규정 문서에 나오는 값("7일" 등)이나 한두 자리 수는 쓰지 않는다. 과제 검증이 시나리오와 에이전트 시스템 프롬프트 전체를 검사한다 (2026-09-19 검토에서 규정 문서의 예시 날짜가 거절 과제의 전달 값과 같아, 조회 없이 예시만 말해도 통과하는 것을 찾아 고쳤다)
- 쓰기 대상 주문은 할인이 0원인 주문으로 한다 (반품 환불액의 할인 안분 규칙은 아직 없다)
- 여러 줄 반품은 한 번에 접수하는 것이 규정이다 (나눠 접수하면 반품 배송비가 두 번 빠져 DB가 달라진다)
- 한 과제에서 같은 부모 아래 같은 테이블에 새로 생기는 행은 1개까지
- 시뮬레이터는 시나리오에 없는 제안(쿠폰, 문의 접수, 반품·교환, 상담원 연결)을 거절하고, 처리를 부탁한 과제에서는 처리가 끝났다는 말을 들은 뒤에만 대화를 끝낸다 (시뮬레이터 지침의 공통 규칙). 2026-09-19 과제 검토에서, 확인 질문에 값이 미리 나와 마지막 쓰기 전에 고객이 대화를 끝낼 수 있는 과제와 요청하지 않은 쿠폰 제안을 고객이 받아들일 수 있는 과제를 찾아 넣었다
- 측정을 시작한 과제는 고치지 않는다. 고치면 시점과 이유를 적고 그 과제를 다시 잰다
- 개발용 과제로 프롬프트와 가드를 고치고, 시험용 과제는 단계가 끝날 때 고른 후보만 한 번 잰다. 시험용 에피소드를 보면서 고치지 않는다

### 무작위성
- 에이전트 temperature 0.0, 시뮬레이터 0.3 (2026-09-19 기준선 첫 실행 뒤 0.7에서 낮춤. 아래 1단계 결과 참조). LLM 호출마다 seed = sha256(기준 seed, 과제, 시도, 역할, 호출 번호). temperature 0에서는 seed가 의미가 없고, 시도마다 달라지는 것은 시뮬레이터의 말이다
- GPU 연산이라 비트 단위 재현은 약속하지 않는다

## 0단계: 스모크 (측정 아님)

`tasks/smoke.yaml`의 과제 5개를 실제 모델로 한 번씩 돌려 에피소드가 끝까지 돌고 판정이 나오는지, 에피소드당 시간이 얼마인지 본다. 수치를 결과로 쓰지 않는다. 이때 확인해 1단계 규칙에 반영할 것:

- 시스템 프롬프트(규정 + 도구)의 실제 토큰 수와 `num_ctx` 16384의 여유
- `prompt_eval_count`가 캐시된 토큰을 포함하는지 (컨텍스트 한도 감지가 의존)
- 에이전트와 시뮬레이터가 같은 모델을 번갈아 쓸 때의 프롬프트 재평가 시간
- 모델이 enum 코드 인자를 제대로 쓰는지, 형식 오류가 얼마나 나는지

### 결과 (2026-09-19, `qwen2.5:7b-instruct`, P0·R0, RTX 2080 Ti, Ollama 0.34.1. 측정 아님)

두 번 돌렸다. 첫 실행 뒤 기준 프롬프트의 기본기를 고쳤고(아래), 그 뒤 다시 돌렸다. 과제 5개를 한 번씩이라 성공 수는 결과로 쓰지 않는다.

| | 첫 실행 (`8450dcc`) | 프롬프트 수정 뒤 |
|---|---|---|
| 성공 | 1/5 | 3/5 |
| 형식 오류 | 7 | 0 |
| 에피소드당 시간 | 56.8초 | 19.4초 |
| 에이전트 LLM 호출당 시간 | 1.9초 | - |

확인한 것
- 에피소드가 끝까지 돌고 판정이 나온다. `infra_error` 0건
- 시스템 프롬프트(규정 + 도구 13개)는 약 3,400토큰이고 대화가 끝날 때 최대 5,160토큰이었다. `num_ctx` 16384에 여유가 있다
- `prompt_eval_count`는 캐시된 토큰을 포함한 전체 프롬프트 토큰 수다 (첫 호출 3,439토큰에 4.3초, 그 뒤로는 토큰 수가 계속 늘면서 프롬프트 평가는 0.04~0.16초). 컨텍스트 한도 검사가 이 값에 기대도 된다
- 에이전트와 시뮬레이터가 같은 모델을 번갈아 불러도 프롬프트 캐시가 유지되고 모델이 다시 로드되지 않는다. 처음 모델을 올리는 데 92초(HDD)
- 도구 호출 id가 온다(13/13). enum 코드 인자(`ordered_by_mistake` 등)는 제대로 쓴다
- P0에서 기한이 지난 반품을 모델이 그대로 접수했고 `return_window_expired` 위반으로 기록됐다. P0와 P1을 가를 여지가 있다

첫 실행에서 본 실패 (하니스가 아니라 모델 행동)
- 고객 이름을 로마자(" PARK Do-yun")로 바꿔 `find_customer`에 넣어 본인 확인에 세 번 실패
- "확인해 보겠습니다, 잠시만 기다려 주세요"라고만 하고 도구를 부르지 않음. 도구를 부르지 않고 "취소가 완료되었습니다"라고 말함
- `<tool_call>` 여는 태그가 깨져(`portun`) 도구 호출이 본문으로 샘: 한 에피소드에서 7번. 규칙대로 구제 실행하지 않았고 그 에피소드는 형식 오류로 끝남
- 시뮬레이터가 중국어로 말하거나, 상담원의 "기다려 주세요"를 따라 말함

그래서 기준 프롬프트에 넣은 것 (측정 전, 스모크 과제만 보고 고침)
- 에이전트: 기다리라는 말 대신 바로 도구를 호출한다 / 도구 성공 결과를 받기 전에는 처리되었다고 말하지 않는다 / 이름과 주문 번호는 고객이 말한 글자 그대로 넣는다 / 항상 한국어로 답한다
- 시뮬레이터: 항상 한국어로만 말한다 / 기다려 달라고 하면 "네"라고만 답한다

2단계 후보로 남긴 것: 본문에 샌 도구 호출을 구제 실행하는 축(F1). 기준선은 구제하지 않는다.

## 1단계: 과제와 기준선 (규칙 2026-09-19, 측정 전)

### 과제 묶음
- `tasks/dev.yaml` 24개: 조회 6, 처리 8, 거절 6, 복합 4
- `tasks/test.yaml` 40개: 조회 8, 처리 14, 거절 10, 복합 8
- 두 묶음은 고객과 주문을 공유하지 않는다 (개발용 `C-91xx`/`O-91xxx`, 시험용 `C-92xx`/`O-92xxx`). 같은 종류의 규정을 다루되 금액, 날짜, 상품, 말투가 다르다
- 쓰기 도구(취소, 반품, 교환, 배송지 변경, 보상 쿠폰, 티켓, 이관)는 두 묶음 모두에 고르게 나온다. 규정 검사 코드는 시험용이 더 넓다: `return_not_delivered`, `coupon_not_eligible`, `coupon_limit_exceeded`, `coupon_order_cancelled`는 시험용에만 있어, 이 네 코드의 실패는 개발용으로 분석할 수 없다 (한계). 거절 과제에는 기한 하루 전후 같은 경계 사례를 넣는다 (기한 마지막 날은 처리, 다음 날은 거절)
- 개발용으로 프롬프트와 가드를 고친다. 시험용은 단계가 끝날 때 고른 구성만 한 번 재고, 시험용 에피소드를 보면서 무언가를 고치지 않는다
- 한계: 시험용 과제 몇 개는 개발용 과제와 구조가 닮았다 (같은 사유 코드나 같은 종류의 경계 사례. 고객, 주문, 금액은 다르다). 2026-09-19 검토에서 7쌍을 찾았고, 측정 전이지만 과제를 다시 쓰지는 않았다

### 기준선
- 구성: P0 · R0 · `qwen2.5:7b-instruct`, 시뮬레이터도 같은 모델. 과제마다 4번
- 재는 것: pass^1~pass^4(과제 단위 부트스트랩 95% 구간), 유형별 성공률, 정답에 없는 쓰기 수, P0에서 통과된 규정 위반 코드별 횟수, 본인 확인 전 접근이 막힌 횟수, 형식 오류 수, 종료 사유별 건수, 에피소드당 시간
- 판정은 없다. 뒤 단계의 비교 기준이 된다
- 실패 분류는 개발용 에피소드로만 한다: 본인 확인 누락, 규정 위반, 잘못된 인자, 고객 확인 없이 실행, 값 전달 누락, 중간에 멈춤, 시뮬레이터 탓
- 시뮬레이터 점검: 개발용 에피소드 20개를 무작위(고정 seed)로 뽑아 읽고, 시나리오에 없는 정보를 지어냄 / 일찍 포기함 / 상담원 역할을 함 / 틀린 확인 요청에 동의함을 센다

### 결과 1: 첫 기준선과 시뮬레이터 점검 (2026-09-19, 커밋 `f4ec9a4`, RTX 2080 Ti) — 시뮬레이터를 고치게 되어 기준선으로 쓰지 않는다

`reports/20260919-093328-qwen2.5-7b-instruct-P0-R0-baseline` (96 에피소드, infra 0, 중단 20, 에피소드당 22.9초)

| pass^1 | pass^2 | pass^3 | pass^4 |
|---|---|---|---|
| 22.9% [11.5%, 35.4%] | 11.8% [2.8%, 22.9%] | 7.3% [1.0%, 16.7%] | 4.2% [0.0%, 12.5%] |

## 5단계: 음성 채널 (규칙 2026-09-21, 측정 전)

텍스트 채팅으로 만든 상담 에이전트 앞에 음성 인식을 붙이면 성공률이 얼마나 떨어지는가, 규칙 기반 정규화로 얼마나 되찾는가를 잰다. 구현은 `src/support_agent/voice/`, 설명은 [voice.md](voice.md).

### 조건 (기준 구성에서 고객 → 에이전트 방향의 입력만 바꾼다)

| 조건 | 에이전트가 받는 고객 발화 |
|---|---|
| V0 | 시뮬레이터가 쓴 글 그대로 (지금까지의 측정) |
| V1 | 글 → 말로 풀어 쓰기(`verbalize`) → 음성 합성 → 음성 인식 → 인식된 글 |
| V2 | V1의 인식된 글 → 규칙 기반 정규화(`normalize_heard`) |

- 나머지는 2단계의 기준 구성 그대로다 (2단계 판정이 "개선 없음"이었으므로): qwen2.5:7b-instruct, P0·R0·G0·F0, 컨텍스트 16k, 시뮬레이터 모델·프롬프트·temperature 같음
- 음성 합성: MeloTTS 한국어(`KR` 화자, 속도 1.0). 발화마다 seed를 `derive_seed(base_seed, 과제, 시도, "voice", 발화 순번)`으로 고정한다. 이 모델을 고른 근거는 같은 PC에서 잰 재인식 오류다 (한국어 CER 5.5%, 사람 녹음 5.4%. voice-translator 저장소의 `docs/experiments.md`)

- 인식 결과가 비면 에이전트에게 `(고객의 말이 인식되지 않았습니다)`를 준다
- 시뮬레이터는 자기가 쓴 글을 기억한다 (사람은 자기가 한 말을 안다). 에이전트 → 고객 방향은 바꾸지 않는다 (고객은 합성음을 알아듣는다고 가정)
- 같은 (말로 푼 글, seed)의 왕복 결과는 `outputs/voice-cache/`에 남겨 다시 쓴다. 같은 입력이면 같은 결과가 나오는 계산이라 측정값을 바꾸지 않는다
- GPU 메모리에 다 들어가지 않으면 음성 합성만 CPU로 돌린다. 어디서 돌렸는지는 manifest의 `voice_channel`에 남는다

### V0은 다시 재지 않는다

### V2의 규칙은 개발용 기록만 보고 만든다

3. 정규화 규칙과 그 테스트를 커밋한 뒤 개발용 V2를 잰다

### 지표
- 1차: pass^1. 과제 단위로 짝지은 부트스트랩(10,000회)으로 차이의 95% 구간 (`analyze compare`)

- 기술용: 글자 오류율(고객이 쓴 글과 에이전트가 받은 글, 공백·문장부호 제외), 엔티티 생존율(전화번호, 이메일, 주문·접수 번호, 금액, 날짜가 도구가 받는 형태 그대로 남았는가), 합성·인식 시간. 이 수치로는 아무것도 판정하지 않는다

- V1은 시험용에 한 번 잰다. V2는 개발용에서 pass^1이나 본인 확인 성공률의 점 추정이 V1보다 높을 때만 시험용에 한 번 잰다

## 7단계: 완료 주장 가드 (계획에 없던 추가 실험. 규칙 2026-09-22, 측정 전)

### 왜 하는가
- 서비스를 실제 모델로 써 보았을 때 7B가 취소 도구를 한 번도 부르지 않고 "취소되었습니다. 12,000원이 환불됩니다"라고 답했다 (DB는 그대로였다. `docs/service.md`). 평가는 이런 에피소드를 실패로 세지만(DB가 정답과 다르다), 서비스에는 그 말이 고객에게 가는 것을 막는 장치가 없다
- 1단계 실패 분류의 "쓰기를 하지 않고 끝남 19건"에 같은 것이 들어 있다. 아래 검출기를 개발용 기준 기록에 대 보면(`analyze claims`) 96 에피소드 가운데 근거 없는 완료 안내가 고객에게 전달된 에피소드가 `...-baseline3`에서 14개(응답 44개), `...-v0-stage5`에서 14개(응답 39개)다. 그 28개 가운데 성공한 에피소드는 1개다. 14B(`...-m1`)에서는 6개(응답 11개)

### 검출기 (`src/support_agent/claims.py`. 개발용 기준 기록만 보고 만들었다)
- 문장 단위로 본다. (1) 끝났다는 말: 완료·접수·처리·변경·발급·제출·등록·신청·연결·생성·취소·반품·교환·환불 뒤에 "되었/됐/했/하였/해 드렸/드렸/마쳤"과 "습니다/어요/으며/고"가 오거나, "남겼습니다". "~하겠습니다", "~되면", "~했는지", 물음표로 끝나는 문장은 해당하지 않는다 (2) 무엇에 대한 말인가: 취소, 반품, 교환, 배송지·주소, 쿠폰, 티켓, 상담원, 환불
- 근거는 그 대화에서 **성공한 도구 결과**다. 쓰기뿐 아니라 조회도 근거가 된다. 그래서 주문을 조회한 뒤 "이 주문은 9월 1일에 이미 취소되었습니다"라고 하는 것은 통과한다

| 종류 | 근거가 되는 도구 결과 |
|---|---|
| 취소 | `"status": "cancelled"` |
| 반품 | 접수 번호 `RT-…` 또는 `"kind": "return"` |
| 교환 | 접수 번호 `EX-…` 또는 `"kind": "exchange"` |
| 배송지 | `change_shipping_address`의 성공 (조회 결과는 지금 배송지를 보여 줄 뿐 "바뀌었다"는 것을 보여 주지 않는다) |
| 쿠폰 | `"coupon_id"` |
| 티켓 | `"ticket_id"` |
| 상담원 연결 | `"handoff_id"` |
| 환불 | 0이 아닌 `refund_won`, 또는 취소·환불 상태 |

- 한 문장이 여러 종류에 걸치면 하나만 근거가 있어도 통과시킨다 (관대한 쪽). 주문 번호가 같은지는 보지 않는다
- 개발용 기준 기록 3개(`...-baseline2`, `...-baseline3`, `...-v0-stage5`, 288 에피소드)에서 걸린 응답 116개(에피소드 46개)를 모두 읽었다. 도구를 부르지 않고 끝났다고 한 것과, 조회 없이 상태·날짜·금액을 지어낸 것("8월 25일에 접수된 반품은 처리되어 환불이 완료되었습니다")뿐이었고 잘못 걸린 것은 찾지 못했다. 성공한 에피소드에서 걸린 것은 1개다 (dev-009 #1: 접수하기 전에 접수했다고 말하고, 그 뒤에 실제로 접수했다). 조회한 사실을 전하는 성공 에피소드(이미 취소된 주문, 이미 접수된 반품, 이미 발급된 쿠폰)는 걸리지 않는다
- 놓치는 쪽: 쓰기가 성공한 직후의 첫 응답 65개 가운데 64개가 "끝났다는 말"로 인식됐다 (나머지 하나는 끝났다는 말이 아니었다). 처음에 놓친 "티켓을 남겼습니다"는 넣었다

- 안내문은 에이전트가 스스로 말한 종류만 되돌려 준다 ("주문 취소에 대해 이미 끝난 것처럼 말했지만 도구 결과에 기록이 없다"). 어떤 도구를 부르라고 하지 않는다. 가드는 정답을 모른다: 처리하면 안 되는 일(거절 과제)이면 "끝났다고 말하지 말고 사실대로 안내"하는 것이 맞는 길이고, 안내문은 두 길을 모두 적는다
- 돌려보낸 응답은 형식 오류로 세지 않고 따로 센다 (멈춤과 같다)
- 본 측정 전에 개발용 과제 4개(기준 기록에서 가장 많이 걸린 dev-007, dev-011, dev-018, dev-023)로 시험 실행을 해서 모델이 안내문을 알아듣는지 본다. 측정이 아니다. 시험 실행을 보고 고친 것은 아래 "시험 실행"에 적고, 고친 뒤에 본 측정을 한다

### 코드 검토 뒤에 고친 것 (2026-09-22, 본 측정 전. 시작했던 C1 측정을 멈추고 기록을 지운 뒤 다시 시작함)

- **연결어미로 이어진 문장**: "본인 확인이 완료되었고, O-1 주문은 취소가 가능합니다", "이미 배송이 완료되었으며 취소는 불가능합니다"가 취소 주장으로 걸렸다 (기록에서는 0건이었지만 거절 과제와 C2의 샘플링에서 나올 수 있고, 걸리면 에피소드가 실패로 끝나거나 안내문이 정답에 없는 취소를 유도한다). 이제 문장을 절(…고/…며/…만/…데 뒤)로 나누고, 끝났다는 말의 종류는 그 절에서 동사 앞(또는 동사 자체)에 있는 것만 본다. "배송이 완료되었습니다"는 택배 이야기이므로 보지 않는다
- "이메일 주소로 본인 확인이 완료되었습니다"가 배송지 변경 주장으로 걸렸다 → "이메일 주소"는 제외
- 놓치던 표현을 넣었다: 조사가 낀 "취소가 되었습니다", "처리를 마쳤습니다", "진행되었습니다", "이루어졌습니다"
- 서비스 전용: 환불액이 승인 기준 이상이면 도구가 `approval_required` 오류로 답하고 요청은 대기열에 남는다. 이때 "취소 요청이 접수되었습니다"는 사실인데 오류 결과는 근거가 아니어서 세 번 막히고 고정 안내가 나갔다. 그 오류를 "접수·신청·등록되었다"는 말의 근거로만 인정한다 ("취소가 완료되었습니다"는 여전히 막는다). 평가(P0, 승인 없음)에는 영향이 없다
- `summary.json`의 형식 오류 수가 돌려보낸 응답(멈춤, 완료 주장)을 세고 있어 `analyze table`과 달랐다 → 같게 맞춤. 검토가 지적한 나머지(관형형 "발급된"을 놓침, 같은 턴에 쓰기가 성공한 뒤 다른 종류의 주장을 세 번 하면 서비스가 "처리하지 못했습니다"라고 답함)는 한계로 남긴다

### 왜 하는가
- 이 프로젝트에서 성공률을 움직인 축은 모델 크기뿐이었다. 2단계 M1(14B)은 개발용 +27.1%p, 시험용 참고 측정 +18.5%p였지만 11GB GPU에 다 올라가지 않아 호출당 시간이 7.8배였고 정답에 없는 쓰기가 늘어 채택하지 않았다. 안내문으로 7B의 행동을 바꾸려던 후보(G1, G2, C1, C2)는 모두 실패했다
- 2단계에서 "새 세대 모델은 뒤로 미룸"이라고 적었다. 그 뒤의 4B 모델은 공개된 도구 호출 벤치마크에서 이전 세대 32B보다 높다: Qwen3-4B-Instruct-2507 모델 카드(2025-08, 비사고 전용) TAU1-Retail 48.7, TAU2-Retail 40.4, BFCL-v3 61.9. APIGen-MT(arXiv 2504.03601) 표의 Qwen2.5-32B-Instruct τ-Retail 24.4. 하니스가 달라 직접 비교는 아니다. 4B는 7B 시뮬레이터와 함께 GPU에 올라갈 가능성이 있어 14B가 걸린 시간 조건을 넘을 수 있다

### 환경이 바뀌어 기준을 모두 다시 잰다
- 공유 설치인 Ollama가 2026-09-29에 0.35.0으로 저절로 올라갔다 (`ollama.exe` 수정일). 2026-10-03에 0.35.1로 올리고 자동 업데이트를 껐다 (사용자 결정). 지금까지의 기록 18개는 모두 0.34.1·0.34.2라 이 단계의 기준으로 쓰지 않는다. 이 단계의 비교와 참조는 모두 0.35.1에서 새로 잰 실행끼리만 한다 (`manifest.json`의 `ollama_version`)
- 이 단계에서 다시 재는 기준은 둘이다
  - **P1·7B**: 비교 기준. 서비스(3단계)가 쓰는 구성이다
  - **P0·7B**: 쓰기 조건의 참조(아래). README "다시 재는 방법"의 기본 명령 그대로 잰다 (`--num-ctx` 16384, 시뮬레이터도 같은 값). 그래서 0.35.1의 텍스트 기준 기록으로 다음 단계(음성 등)에도 쓸 수 있다. 쓰기 수만 참조하고 pass^1을 짝짓지 않으므로 컨텍스트 값이 달라도 된다 (num_ctx는 한도 안의 출력을 바꾸지 않고 KV 캐시 크기만 정한다)

### 재기 전에 고친 것 (판정자의 측정 계획과 다른 점과 그 이유)
1. **컨텍스트는 모든 팔에서 에이전트 = 시뮬레이터 = 12288**. 계획은 "시뮬레이터는 모든 팔에 8k, 에이전트 num_ctx는 후보끼리 같게"였다. 그대로 하면 기준 팔(에이전트와 시뮬레이터가 같은 qwen2.5 7B)에서 두 역할의 num_ctx가 달라지는데, Ollama는 모델 하나에 실행기 하나를 두고 실행기 옵션(num_ctx, num_gpu)이 다른 요청이 오면 모델을 다시 읽는다. 매 턴 다시 읽게 된다. 그래서 한 값으로 맞추고, 실행기는 같은 모델에 다른 실행기 옵션을 주면 시작하지 않게 했다
   - 12288인 이유: 지금까지 기록의 에이전트 최대 프롬프트는 7,900토큰(14B 시험용)이고, 14B가 8192에서 컨텍스트 한도로 끝난 에피소드가 있었다 (개발용 1, 시험용 5). 12288의 95% 한도는 11,673토큰이다. 시뮬레이터의 최대 프롬프트는 4,995토큰이라 시뮬레이터에는 어느 값이든 출력이 같다
   - 비용: qwen3 4B의 KV 캐시는 토큰당 144 KiB(36층 × KV 헤드 8 × 128 × 2 × fp16)라 12288에서 1.7 GiB다. 가중치 2.3 GiB와 계산 버퍼를 더해 약 4.4 GiB, 7B 시뮬레이터는 약 5.4 GiB(KV 토큰당 56 KiB)로 합계 약 9.8 GiB로 추정한다. 지금까지 실행이 시작될 때 다른 프로그램이 쓴 GPU 메모리가 983~2,876 MiB였으므로 함께 다 올라가지 못할 수 있다 → 아래 스모크 관문 S1과 "시뮬레이터 자리" 사다리
2. **실행기 옵션** (`run.py`): `--user-num-ctx`(시뮬레이터 전용 컨텍스트. 기본은 `--num-ctx`와 같아 이전 명령은 그대로 돈다), `--user-num-gpu N`(시뮬레이터 층 N개만 GPU에), `--think on|off`(에이전트에만). manifest의 `config.user_num_ctx`, `user_provider.num_gpu`, `agent_provider.think`에 남는다. 실행이 끝날 때 `/api/ps`(모델별 `size`, `size_vram`)를 `summary.json`의 `ollama_ps_at_end`에, 모델을 올린 직후 것을 manifest의 `ollama_ps_after_preload`에 남긴다
3. **쓰기 조건** (아래 선택 규칙 2). 2단계 규칙("정답에 없는 쓰기가 기준보다 늘지 않음")을 P1·7B 기준에 그대로 쓰면 결과가 재기 전에 정해진다. P1·7B는 거의 행동하지 않아(0.34.2 기록에서 성공한 쓰기 10건) 정답에 없는 쓰기가 2건이고, 더 자주 행동하는 모델은 규정 위반이 막혀도 위반이 아닌 잘못된 쓰기(다른 대상, 쿠폰, 티켓)를 거의 확실히 2건 넘게 한다 (14B는 정답에 없는 쓰기 18건 중 위반이 아닌 것이 7건)
4. **시뮬레이터 자리**: 계획은 "시뮬레이터를 CPU로 옮겨야 하는 후보는 개발용만 재고 멈춘다"였다. 이유는 비용이다 (CPU 시뮬레이터는 에피소드당 약 140초: 개발용 3.7시간, 시험용 6시간). 그 규칙은 그대로 두고, 층 일부만 CPU로 옮기는 중간 단계를 넣었다. 층 일부만 옮긴 후보는 시험용까지 간다. 같은 가중치·같은 설정이고 CPU와 GPU의 계산 차이는 이 프로젝트가 이미 받아들인 GPU 비결정성과 같은 종류다 (2단계 M1의 시험용 참고 측정도 CPU 시뮬레이터였다)

### 고정하는 것
- 시뮬레이터: `qwen2.5:7b-instruct`, temperature 0.3, 프롬프트 그대로. 이 단계 안에서 바꾸지 않는다
- 기준과 후보 모두 P1 · R0 · G0 · F0 · C0 · V0 · L0, 과제·규정·프롬프트·seed 그대로
- 다중 도구 호출은 지금처럼 첫 호출만 실행하고, 버린 호출 수를 판정 표 옆에 적는다 (14B는 33·49로 많았다. 병렬 호출을 많이 내는 모델에 불리할 수 있다. 한계로 적는다)

**시뮬레이터 자리 사다리** (S1을 어길 때, 위에서부터)
1. GPU가 쉬고 있지 않았으면(아래 "시간 수치의 조건") 쉴 때까지 최대 60분 기다렸다가 같은 스모크를 한 번 더
2. 시뮬레이터 층 일부를 CPU로: `--user-num-gpu 24`, 안 되면 20, 16. 이때 S1은 "에이전트 100% GPU, 시뮬레이터가 GPU에 일부라도 있음, 다시 읽기 0"이다. 여기서 정한 자리로 그 후보의 개발용·시험용을 모두 잰다
3. 그래도 안 되면 `--user-on-cpu`. 이 후보는 개발용만 재고 시험용은 재지 않는다 (판정자 계획)

### 개발용 측정 (24과제 × 4회, `--official`)
- 순서: P1·7B 기준 → P0·7B 참조 → M2a → M2b(스모크를 통과했으면)
- GPU 상한은 이 단계 전체 8시간이다. 실행마다 시작 전에 남은 시간을 계산한다 (에피소드당 시간은 스모크 값, 기준은 지금까지의 기록). M2a가 선택 조건을 만족했는데 M2b 개발용과 시험용 세 실행을 함께 넣을 시간이 없으면 M2b를 재지 않고 그렇게 적는다

### 선택 규칙 (개발용)
`analyze select <P1·7B> <P0·7B> <M2a> [<M2b>]` (후보는 작은 모델부터)
1. pass^1의 기준과의 차이(과제 단위 짝지은 부트스트랩, `analyze compare`와 같은 계산)가 +5%p 이상
2. 통과된 규정 위반 0건, 그리고 **정답에 없는 쓰기가 P0·7B 참조(이 단계에서 0.35.1로 잰 값) 이하**. 0.34.x에서 세 번 잰 P0·7B 개발용 값은 11, 12, 11이었다 (`analyze table`로 다시 계산한 `...-baseline2`, `...-baseline3`, `...-v0-stage5`. 2026-10-03 메모: 7단계 결과에 "기준을 세 번 잰 값(12, 12, 11)"이라고 적은 것은 잘못 옮긴 것이고, 그 문단의 결론은 같다). P1에서는 위반이 도구에서 막히므로 통과된 위반은 구조상 0이다. 0이 아니면 도구 버그로 보고 멈춘다
3. 에이전트 LLM 호출당 평균 시간이 기준(P1·7B)의 3배 이하
4. 셋을 모두 만족한 후보가 여럿이면 pass^1이 높은 쪽, 같으면 작은 모델(M2a)
5. 짝짓기: `same-setup`의 항목 가운데 에이전트 모델(digest, think 포함)만 달라야 한다. 시뮬레이터 자리(`num_gpu`)는 위 사다리대로 달라도 되고 표에 적는다
6. 만족한 후보가 없으면 시험용은 재지 않고 **"개선 없음"**으로 적는다
- 보고만 하는 것: pass^4, 버린 호출, 형식 오류, 한자 섞인 답, 컨텍스트 한도 종료, 쓰기 정밀도(정답과 맞는 쓰기 / 성공한 쓰기 전체. P1·7B는 0.34.2 기록에서 10건 중 8건이라 기준값 자체가 크게 흔들려 조건으로 쓰지 않는다), prompt_eval 시간

쓰기 조건의 뜻: 새 모델이 서비스 구성(P1)에서 하는 잘못된 쓰기가, 이 프로젝트가 기준선으로 삼았던 7B(규정이 프롬프트에만 있는 P0)의 잘못된 쓰기보다 많지 않아야 한다. P1·7B(2건 수준)보다 느슨하다. 그래서 아래 판정이 "개선"이어도 서비스의 모델은 이 단계에서 바꾸지 않는다

### 판정 (시험용 40과제 × 4회, 채택한 후보가 있고 그 시뮬레이터가 전부 CPU가 아닐 때만)
P1·7B 기준, P0·7B 참조(기본 명령), 고른 후보를 한 번씩 잰다. `analyze verdict <P1·7B> <P0·7B> <후보>`. 2단계 판정표와 같고, 조건 2의 기준만 P0·7B 참조로 바꾼다
1. pass^1 차이(후보 − P1·7B)의 95% 구간이 0보다 위
2. 정답에 없는 쓰기가 P0·7B 시험용 참조 이하 (통과된 규정 위반은 구조상 0)

| 1 | 2 | 판정 |
|---|---|---|
| 만족 | 만족 | **개선** |
| 만족 | 불만족 | **성공률은 올랐지만 위험한 쓰기가 늘었음** |
| 불만족 | - | **개선을 확인하지 못함** |

pass^4 차이, 유형별 성공률, 버린 호출, 형식 오류는 함께 보고하되 판정에 넣지 않는다. 시험용 에피소드는 결과를 적은 뒤에도 무엇을 고치는 데 쓰지 않는다

### 해석 보조: 시뮬레이터 점검 (관찰만)
- 기준(P1·7B)과 잰 후보마다, 두 개발용 기록에서 같은 (과제, 시도) 20개를 뽑아 구성 이름과 판정을 가리고 섞어 읽는다 (`analyze blind <기준> <후보> --n 20 --out <폴더>`). 1단계 점검표로 적고(`marks.json`: 결과를 바꿨을 만한 잘못, 지어냄, 일찍 끝냄, 상담원처럼 말함, 기다려 달라고 함, 틀린 안내에 동의, 시나리오에 없는 제안 수락, 다른 언어), `analyze unblind <폴더>`로 실행별로 센다
- 무엇도 고르지 않고 판정을 바꾸지 않는다. 강한 에이전트에서 시뮬레이터의 잘못이 결과를 더 좌우하는지 보려는 것이다. 시험용 기록은 읽지 않는다
- 한계: 읽는 쪽이 이 프로젝트를 만든 쪽(Claude)이고, 대화의 말투로 구성을 짐작할 수 있다

### 시간 수치의 조건

## 9단계: 음성 V4 — 발신 번호로 하는 본인 확인 (계획에 없던 추가 실험. 규칙 2026-10-04, 측정 전)

### 왜 하는가
- 5단계에서 음성 채널은 본인 확인에서 무너졌다 (시험용 V0 73.1% → V2 27.5%). 개발용 V2 기록(`20260921-145634-...-V2-v2`)에서 본인 확인에 실패한 에피소드 50개를 다시 나눴다 (`work/improve-1003/p3_ident_breakdown.py`, 로컬 전용): `find_customer`를 부르지 않음 21, 받아 적은 연락처가 틀림 22 (그중 이름도 틀림 3), 연락처는 맞고 이름만 틀림 5, 이름과 연락처가 한 호출 안에서 함께 맞은 적이 없음 2. 부르고도 실패한 29개 가운데 시나리오가 이메일을 주는 과제가 19, 전화번호를 주는 과제가 10이다
- 5단계의 결론이 "음성 상담의 본인 확인은 불러 주는 값을 받아 적는 방식이 아니라 다른 수단(발신 번호, 되읽어 확인하기, 자릿수 검사 뒤 다시 묻기)이 필요하다"였다. 이 단계는 그중 발신 번호(ANI)를 잰다. 받아 적는 경로 자체를 없애므로 연락처가 틀린 22개를 겨냥하고, 이름의 작은 허용 오차가 이름만 틀린 5개를 겨냥한다
- 본인 확인의 뜻이 바뀌는 설계 변경이다. 2026-10-02 사용자가 이 변경을 승인했고, 결과는 **설계 변경의 효과**로만 보고한다 (아래 "읽는 법")

### V4가 바꾸는 것 (V2에서)
| | V2 | V4 |
|---|---|---|
| 고객의 말 | 합성 → 인식 → V2 정규화 | 같다 (같은 채널, 같은 캐시) |
| 본인 확인 도구 | `find_customer(name, contact)`: 받아 적은 이름과 연락처가 모두 정확히 맞는 고객 | `verify_caller(name)`: 발신 번호로 가입한 고객 **한 명**의 이름과, 정규화(NFKC, 공백, 끝의 `님`·`고객님` — `find_customer`와 같다) 뒤 **자모 편집 거리 1 이하**면 통과 |
| 발신 번호 | 없음 | 하니스가 과제의 고객(`customer_id`)이 가입한 전화번호를 대화의 도구 문맥(`ToolContext.caller_phone`)에 넣는다. 에이전트에게는 보이지 않는다 |
| 시스템 프롬프트 | 그대로 | 규칙 목록 끝에 한 줄 (`prompts/caller_id.md`): "이 상담은 전화로 합니다. 규정 2의 본인 확인은 가입 연락처 대신 발신 번호와 이름으로 합니다: 고객에게 이름을 묻고 verify_caller 도구로 확인합니다. 전화번호나 이메일은 묻지 않습니다." |

- `verify_caller`는 1:N 검색을 하지 않는다. 번호가 고객 한 명을 가리키고, 이름은 그 한 명과만 비교한다. 에이전트는 후보를 보지 못한다. 통과하면 `find_customer`와 같은 키(`customer_id, name, grade, grade_label`)를 돌려주고 이름은 등록된 이름이다. 거절 코드는 `name_mismatch`(이름이 다름), 하니스가 쓸 번호를 주지 못한 경우인 `no_caller_number`, `caller_not_registered`, `caller_shared`(번호 하나에 고객이 여럿. seed의 전화번호 109개는 모두 다르다). 대화당 고객 1명(`already_verified`)은 그대로다
- 모든 과제의 고객이 가입한 번호로 건다고 본다. 시나리오가 이메일만 주는 과제도 같다
- 바꾸지 않는 것: 시뮬레이터(모델·프롬프트·temperature), 과제, 판정, 규정 문서(`policy.md`), 채널(MeloTTS `KR`, faster-whisper `large-v3-turbo` fp16 beam 5, V2 정규화). 시뮬레이터는 V4를 모르므로 지금처럼 연락처를 불러 줄 수 있다
- V0~V2의 시스템 프롬프트와 도구 목록은 바이트까지 그대로다. 테스트가 지금까지 개발용 기록의 manifest 해시(`agent_system` `7238ce2b…`, `tools` `565d3ecc…`)로 고정한다 (`tests/test_stage9.py`). 서비스와 MCP 서버는 `build_registry()`의 기본값이라 `find_customer` 그대로다 (서비스 코드는 바뀌지 않아 HawkScan 대상이 아니다)
- V3은 쓰지 않는다

### 재기 전에 정한 것 (판정자 계획의 세 항목)
1. **k = 1** (`tools.NAME_TOLERANCE`). 개발용 V1·V2 기록의 이름 오인식만 보고 정했다 (`work/improve-1003/p3_name_errors.py`, 로컬 전용. 시험용 기록은 보지 않았다)
   - `find_customer`에 넣은 이름이 고객 이름과 다른 호출: V1 92건, V2 54건. 자모 거리별로 1: 82 + 49 = 131, 2: 3 + 3 = 6, 3: 1 + 1 = 2, 5 이상: 6 + 1 = 7 (받아 적은 이름이 아니라 에이전트가 지어낸 이름이나 상품명. "김상호", "변과류 선물 세트")
   - 서로 다른 오인식 이름은 V1 19개 중 16개, V2 17개 중 14개가 거리 1이다 (배성훈 → 배성분, 채민서 → 최민서, 하도경 → 하도병, 허윤서 → 허윤설). 거리 2는 안재희 → 안재기, 송민규 → 송민리, 노경민 → 노병린, 채민서 → 최민설이고, 모든 인식이 거리 2였던 과제는 dev-007 하나다
   - k = 1이 받아 적은 이름의 오인식 대부분(지어낸 이름을 빼면 139건 중 131건)을 덮는다. k = 2는 호출 6건을 더 덮는 대신 한 음절의 초성과 모음을 함께 바꾼 다른 이름(예: 민준 ↔ 민정)까지 받아들인다. 작은 쪽을 고른다
   - 이 결정은 아래 충돌 검사를 하기 전에 커밋한다
2. **`find_customer`는 V4에서 뺀다.** 도구 목록에 없고, 불러도 `unknown_tool` 오류다 (도구 오류로 세어 한도 10에 들어간다). 받아 적은 연락처로 찾아 주는 대체 경로는 두지 않는다
   - 남기면 받아 적은 연락처의 1:N 검색이 V4 안에 그대로 남아 V2의 실패 경로가 섞이고, 받아 적은 연락처가 우연히 다른 고객과 맞으면 발신자가 아닌 고객이 확인되어 1:1이 깨진다
   - 모든 과제의 고객이 가입 번호로 건다고 보므로 대체 경로가 필요한 과제가 없다. 실제 서비스라면 번호를 숨긴 전화, 가입하지 않은 번호의 전화를 위한 대체 경로가 필요하다 (한계)
3. **짝짓기**: `analyze same-setup <V2> <V4> --ignore voice --ignore-prompt tools agent_system`. 이 두 해시 말고 다른 항목(설정, 과제·seed·정책·시뮬레이터 프롬프트 해시, 두 제공자, 판정된 시도)이 다르면 V2를 다시 잰다

### 관문: 이름 허용 오차 충돌 검사 (CPU, 이 규칙을 커밋한 뒤 바로)
- `analyze name-collisions --k 1`: seed DB 고객 109명 각각의 번호(A)로 건 전화에서 다른 고객 B의 이름을 말했을 때 `verify_caller`가 받아들이는 순서쌍 (A, B)를 센다. 이름이 글자까지 같은 쌍(동명이인)은 따로 센다: 지금의 정확한 비교(k = 0)도 받아들이고, 확인되는 고객은 번호의 주인 A라서 허용 오차 탓이 아니다
- **0건이어야 측정으로 간다.** 1건 이상이면 이 단계를 멈추고 그렇게 적는다. k는 바꾸지 않는다
- 이것은 보안 지표가 아니다. 허용 오차가 이 DB의 다른 이름을 받아들이는지만 본다. 발신 번호 위조, 기기 탈취(본인 전화를 가진 사람은 이름을 안다), 가족이 번호 하나를 같이 쓰는 경우는 범위 밖이다. 실제 서비스라면 일회용 인증 번호나 추가 질문을 붙여야 한다

### 판정 (시험용 40과제 × 4회, V2와 V4를 한 번씩)
- **본인 확인**: V4 − V2 본인 확인 성공률 차이의 95% 구간이 0보다 위면 "**발신 번호 확인이 본인 확인을 되찾는다**", 아니면 "본인 확인의 차이를 확인하지 못함"
- **pass^1**: V4 − V2 pass^1 차이의 95% 구간이 0보다 위면 "**발신 번호 확인이 pass^1을 되찾는다**", 아니면 "pass^1의 차이를 확인하지 못함"
- 두 문장을 따로 적는다. V4 − V0(8단계의 시험용 P0·7B 참조)는 관찰로만 적는다. 정답에 없는 쓰기와 통과된 규정 위반은 함께 보고하되 판정에 넣지 않는다 (본인 확인이 늘면 쓰기의 기회도 는다)
- 시험용 에피소드는 결과를 적은 뒤에도 무엇을 고치는 데 쓰지 않는다

### 왜 하는가
- 8단계 시험용에서 `qwen3.5:4b`(M2b)는 7B보다 훨씬 자주 행동했고(성공한 쓰기 27 → 100), 정답에 없는 쓰기가 13건이었다 (서비스 구성이던 P1·7B는 6건). 서비스의 사람 승인(환불액 10만 원 이상)은 13건 가운데 어느 것도 막지 못했을 것이다 (8단계 날짜 메모, `59cbbec`). 2026-10-04 서비스의 기본 모델이 M2b로 바뀌어 이 공백이 서비스에 그대로 있다. 사용자가 이 공백을 겨냥한 이 가드를 다음 후보 1순위로 정했다
- `docs/plan.md`는 R2를 재지 않은 이유로 "7B의 실패가 확인 없이 실행한 것이 아니라 실행하지 않은 것"이라고 적었다. M2b는 실제로 행동하므로 그 전제가 이제 맞지 않는다. 다시 제안하는 것이 아니라 처음 재는 것이다
- 규정 3("처리 전 고객 확인")은 지금도 DB를 바꾸기 전에 내용을 말하고 명시적 동의를 받으라고 한다. τ-bench의 retail·airline 정책도 결과가 남는 동작 전에 내용을 말하고 명시적 동의("yes")를 받게 한다 (arXiv 2406.12045). 지금은 이것이 프롬프트에만 있다. R2는 도구 쪽에서 강제한다
- 개발용 M2b 기록(`20261003-200306-...-m2b`)에서 성공한 쓰기 39건 앞의 대화를 읽었다 (`work/stage10/writes_context.py`, 로컬 전용): 상담원이 내용을 묻고 고객이 "네"라고 한 뒤의 쓰기가 많지만, 고객이 빠진 인자(취소 사유 등)를 말하자마자 묻지 않고 실행한 쓰기도 있다(dev-007 #0·#3, dev-021 #2·#3, dev-023 #0, dev-024 #0 등). 정답에 없는 쓰기 3건은 상담원 연결 2건(dev-015 #0: 고객이 "아, 그래요? 그럼 어떻게 해야 하나요?"라고 물었는데 연결, dev-023 #1: "네, 수령일은 모르겠어요."에 연결)과 다른 주문 번호로 남긴 티켓 1건(dev-023 #3)이다

### 개발용 측정 (24과제 × 4회, `--official`)
- R2 한 실행만 잰다. 기준은 8단계 M2b 개발용 기록이다 (위 3)
- `analyze same-setup <M2b 개발용> <R2> --ignore reasoning`이 "same setup"이 아니면 짝지을 수 없다. infra 오류로 판정된 시도가 달라도 그렇다: 같은 명령으로 한 번 다시 재고, 그래도 아니면 멈추고 사람에게 넘긴다
- 개발용은 쓰기가 3건뿐이라 안전 효과를 가를 힘이 없다. 그래서 개발용 조건은 비용만 본다 (`analyze confirm-check <M2b 개발용> <R2>`)

  - 통과된 규정 위반은 P1에서 구조상 0이다. 0이 아니면 도구 버그로 보고 멈춘다
- D1과 D2를 모두 만족하면 시험용으로 간다. 아니면 시험용은 재지 않고 "개선을 확인하지 못함 (개발용 비용 조건 불만족)"으로 적는다

## 11단계: 음성 현실 조건 V4-R, A단계 — 생성 소음, 8 kHz μ-law, 프레임 손실에서 인식만 잰다 (계획에 없던 추가 실험. 규칙 2026-10-05, 측정 전. LLM 없음, 판정 없음)

### 왜 하는가
- 지금까지의 음성 수치(5·9단계)는 모두 깨끗한 합성 음성(MeloTTS → turbo)에서 나왔다. 실제 통화보다 쉬운 조건이라 상한에 가깝고(5단계 "재기 전에 적는 한계", README 한계), "실제 통화 음성으로 다시 재기"는 남은 질문으로만 적혀 있었다 (`docs/plan.md`)
- τ-Voice(arXiv 2603.13686, 2026-03-14)가 음성 상담 평가에 쓰는 열화 구성 "Realistic"을 공개했다: 배경 소음 15 dB(±3 dB 변동), 돌발 소음 분당 1회(−5 ~ +10 dB), 발화의 20%에 먹먹함, G.711 μ-law 8 kHz, Gilbert–Elliott 프레임 손실(평균 2%, 100 ms 묶음). 깨끗한 조건에 비해 pass@1이 31–51%에서 26–38%로, 제공자별로 5~14%p 떨어졌고, 논문은 주된 실패를 이름·이메일을 받아 적지 못해 막힌 본인 확인으로 적는다 (2026-10-04 확인. 학회 표기는 논문의 키워드에만 있어 적지 않는다)
- 9단계 V4는 본인 확인을 "발신 번호 + 이름이 글자까지 같음"(k = 0)으로 바꿨다. 이름 받아쓰기에 기대는 설계라, 전화 음질에서 이름이 얼마나 살아남는지가 이 설계의 약한 곳이다
- 같은 PC에서 turbo는 전화 대역·μ-law만으로 Zeroth 시험 글자 오류율이 4.48% [3.77, 5.32]에서 6.38% [5.46, 7.35]로 올랐다 (whisper-ko-ft 4단계. 사람이 녹음한 음성, 소음과 손실 없음)

### 이 단계가 재는 것 (A단계)
- 9단계 V4 개발용 실행 `reports/20261004-154016-qwen3.5-4b-P0-R0-G0-F0-V4-v4-k0`(24과제 × 4회)의 고객 발화 929개(합성한 것 전부)를 그 실행과 같은 말로 푼 글과 같은 합성 seed(`derive_seed(1000, 과제, 시도, "voice", 순번)`)로 다시 합성한다. faster-whisper가 녹음을 읽을 때와 같은 방법(`decode_audio`)으로 16 kHz로 바꾼 뒤, 같은 인식기(`large-v3-turbo` fp16, beam 5, VAD 끔)로 두 번 받아 적는다: 그대로(**깨끗한 음성**)와 아래 열화를 거친 것(**열화한 음성**). 두 받아쓰기 모두 V2 정규화(`normalize_heard`)를 거친다. 같은 소리의 두 조건을 짝지으므로 차이는 열화의 몫이다
- LLM은 쓰지 않는다. 에이전트가 열화한 받아쓰기로 무엇을 하는지(B단계, 에피소드)는 재지 않는다 (아래)
- 이 단계는 개선 후보가 아니라 측정 조건이다. **채택 판정이 없다.** 결과는 "현실 조건 차이"로 README의 결과와 한계에 적는다
- 시험용 과제의 기록은 열지 않는다 (시험용 V4 기록도 없다). 실행기는 시험용 기록을 원본으로 받지 않는다

### 열화 V4-R (`src/support_agent/voice/degrade.py`, 버전 `v4r-1`)
값은 τ-Voice Realistic이다 (논문 표 4·표 13. 논문이 적지 않은 먹먹함의 구간 길이와 차단 주파수는 공개 코드 tau2-bench `voice_config.py`의 기본값). 개발용 결과를 보고 고치지 않는다. 구현은 이 저장소에서 했고 tau2-bench 코드(MIT)는 옮기지 않았다. 순서는 τ-Voice와 같다: 말소리 효과 → 소리 환경 → 채널.

| 순서 | 효과 | 값 |
|---|---|---|
| 1 | 먹먹함 | 발화의 20%. 한 구간 500 ms를 1500 Hz 저역 통과(4차 버터워스, 위상 지연 없음)로 바꾸고, 앞뒤 100 ms에 걸쳐 섞어 들어가고 나온다. 구간 위치는 무작위 |
| 2 | 배경 소음 | 분홍 또는 갈색 생성 잡음(반씩), 20 Hz 아래는 없음. SNR은 발화마다 15 dB ±3 dB에서 고르게 하나 |
| 3 | 돌발 소음 | 분당 1회(포아송, 발화 길이에 비례), 하나마다 SNR −5 ~ +10 dB에서 고르게. 생성한 소리 넷 중 하나: 부딪는 소리(0.25 s, 줄어드는 잡음), 전화벨(1.0 s, 1000·1250 Hz가 25 ms씩 번갈아), 경적(0.6 s, 420 Hz와 배음), 사이렌(1.5 s, 650 → 1300 → 650 Hz). 위치는 무작위이고 발화 끝을 넘는 부분은 잘린다 |
| 4 | 음량 | 섞은 소리의 최댓값이 0.99를 넘으면 발화 전체를 낮춰 0.99로 맞춘다 (코덱에서 잘리는 대신) |
| 5 | 전화 대역, 8 kHz, μ-law | whisper-ko-ft `channel.py`의 `telephone()`과 같은 구현: 300–3400 Hz 대역 통과(4차 버터워스), 8 kHz로, 8비트 μ-law 왕복. 그 저장소의 코드로 계산한 출력값으로 테스트에 고정했다 |
| 6 | 프레임 손실 | 8 kHz 신호의 20 ms 프레임에 Gilbert–Elliott: 나쁜 상태의 프레임은 모두 잃고 좋은 상태는 잃지 않는다. 평균 손실 2%, 잃는 구간 평균 100 ms(5프레임). 잃은 프레임은 무음이다 (메움 없음) |
| 7 | 16 kHz로 | 인식기에 넣는다 |

- SNR(배경·돌발)은 말소리와 소음 모두 **전화 대역(300–3400 Hz) 안에서** 잰 RMS의 비다. 말소리 쪽은 그 발화 전체(먹먹함 전)다
- 무작위는 모두 `derive_seed(1000, 과제, 시도, "degrade", 순번)`에서 나오고 효과마다 따로 갈라 쓴다 (한 효과의 뽑기가 다른 효과를 움직이지 않는다). 매개변수와 버전은 결과 기록(`manifest.json`의 `degrade`)과 왕복 캐시(`outputs/voice-cache/v4r-roundtrips.jsonl`)의 키에 들어간다

**τ-Voice·판정자 계획과 다르게 정한 것 (재기 전에, 이유와 함께)**
- 소음은 생성한다. τ-Voice는 녹음(거리, 사람 말소리 / 전화벨, 개 짖는 소리 등)을 섞는다. 이 저장소에는 쓸 녹음이 없고 내려받지 않는다. 연구자 제안의 "같은 MeloTTS 화자로 만든 웅성거림"은 쓰지 않는다: 고객과 같은 목소리라 인식기가 소음 쪽 말을 받아 적을 수 있어, 소음과 다른 교란이 섞인다 (검토자 정정, 판정자 계획)
- SNR을 전화 대역 안에서 잰다. τ-Voice는 고정한 기준 말소리 크기에 맞춘다. 갈색 잡음은 힘의 대부분이 300 Hz 아래라 채널이 걸러 내므로, 전 대역으로 재면 갈색이 분홍보다 훨씬 쉬운 조건이 된다
- 배경 소음 크기는 발화마다 한 번 뽑는다 (τ-Voice는 한 통화 안에서 천천히 흔든다). 발화가 평균 5.7초라 차이가 작다
- 말소리 끼어들기(분당 0.7회)와 기침 같은 소리는 넣지 않는다. 같은 목소리를 다시 써야 하고, 받아쓰기보다 차례 주고받기의 문제다
- μ-law는 whisper-ko-ft의 구현(연속 μ-law를 256단계로 양자화)이다. G.711의 구간 표와 조금 다르다. 프레임 손실을 코덱과 16 kHz 복원 사이에 넣으려고 `telephone()`을 두 함수(`narrowband`, `widen`)로 나눴다. 나눈 두 함수를 이어 붙이면 `telephone()`과 출력이 같다 (테스트)
- 44.1 kHz → 16 kHz는 연구자 제안처럼 따로 하지 않고, 측정한 채널과 같은 `decode_audio`(PyAV 리샘플러)를 쓴다. 깨끗한 음성이 9단계 채널과 같은 소리가 되게 하려는 것이다
- 판정자 계획에 없던 것 둘을 더했다: 재현 확인(깨끗한 쪽이 9단계 기록과 같은지)과 열화 조건을 뽑기만 하는 CPU 관문 (아래)

### 지표 (깨끗한 음성 대 열화한 음성, 같은 발화의 짝)
- **글자 오류율**: 말한 글(`said`)과 정규화 뒤 받아쓰기에서 공백·문장부호를 빼고 잰 편집 거리의 합 / 말한 글자 수의 합 (`analyze voice`의 "글자 오류율"과 같은 계산)
- **이름 정확 생존 (k = 0)**: 말한 글에 과제 고객의 등록 이름이 (공백을 빼고) 들어 있는 발화 가운데, 받아쓰기에도 그 이름이 글자까지 같게 들어 있는 비율. `verify_caller`가 받아들이는 기준과 같다. 개발용 V4 발화 중 165개
- **주문·접수 번호 생존**: V2 정규화 뒤, `analyze voice`의 엔티티 규칙 그대로 (126개)
- **이메일 생존**: 같은 규칙. V4는 연락처를 묻지 않아 발화가 12개뿐이라 기술용이다. 전화번호(29), 금액(24), 날짜(43)도 함께 적되 기술용
- 기술용: 그대로 전달(정규화 뒤 받아쓰기가 말한 글과 같음), 인식 안 됨(빈 받아쓰기), 효과별 글자 오류율(프레임 손실·먹먹함·돌발 소음이 있는 발화와 없는 발화, 분홍과 갈색. 구간 없음), 실제로 들어간 조건(먹먹함 비율, 잃은 프레임 비율, 돌발 소음 수, SNR 범위, 음량을 낮춘 발화 수)
- 구간: 각 지표의 (열화 − 깨끗함) 차이를 과제 24개 단위로 다시 뽑는 부트스트랩(10,000회, seed 20261005)의 95% 구간. 한 과제의 발화는 함께 뽑히고, 비율은 뽑힌 과제를 모두 합쳐 계산한다 (분모가 0인 뽑기는 버린다)
- 표는 `voice_real report <실행>`이 낸다. 모델 없이 기록에서 다시 계산된다

### 재현 확인 (재기 전에 정함)
- 다시 합성한 깨끗한 음성의 받아쓰기가 9단계 기록의 받아쓰기(`heard`)와 글자까지 같은 발화가 **90% 이상**이면, 깨끗한 쪽 수치를 9단계 V4 채널과 같은 것으로 적는다
- 90% 미만이면(합성·인식의 GPU 비결정성 등) 짝지은 차이는 그대로 적되(같은 소리의 두 조건이라 짝은 유지된다), 깨끗한 쪽을 9단계 수치와 잇지 않고 그렇게 적는다. 이것 때문에 다시 재지는 않는다
- 음성 모델(MeloTTS·torch·faster-whisper·ctranslate2 버전, turbo fp16, beam 5, VAD 끔, 장치 cuda)이 9단계 기록과 하나라도 다르면 공식 실행은 시작하지 않는다 (`voice_real run --official`이 거절한다)

### 관문 (CPU, 이 규칙을 커밋한 뒤 GPU 전에)
`voice_real plan reports/<9단계 V4 개발용>`: 929개 발화마다 기록된 길이로 열화 조건만 뽑아(소리 없이) 등록한 비율과 맞는지 본다. 구현을 데이터 크기에서 확인하는 것이고, 아무것도 재지 않는다
- 먹먹한 발화 15~25%, 잃은 프레임 1~3%, 돌발 소음 수가 포아송 기댓값(오디오 분 × 1) ±3 표준편차 안, 배경 SNR이 모두 12~18 dB이고 분홍·갈색이 모두 나온다
- 하나라도 어기면 GPU로 가지 않고 구현을 확인한다. 고치면 이유를 날짜 메모로 적고 커밋한 뒤 다시 돈다 (매개변수는 바꾸지 않는다)
- 실제 실행은 다시 합성한 소리의 길이로 뽑으므로 관문의 수와 조금 다를 수 있다 (seed가 같고 길이가 같으면 조건도 같다)

### 하니스 확인 (CPU, 측정 아님)
- `voice_real run <9단계 V4 개발용> --device cpu --limit 3`: 합성·인식을 CPU로 세 발화만, `outputs/v4r/`에 쓴다 (음성 모델이 9단계와 다르다는 경고가 나오는 것이 맞다). 코드 경로만 확인한다. 받아쓰기는 결과로 쓰지 않는다

### 예상 (재기 전에 적음)
- 깨끗한 음성: 9단계 V4 기록과 비슷하다 — 글자 오류율 4.39%, 이름 99/165 (60%), 주문·접수 번호 81/126 (64%), 이메일 7/12 (기록된 받아쓰기로 센 값)
- 열화한 음성: 글자 오류율 7~12%, 이름 35~55%, 주문·접수 번호 40~60%. 모든 생존율은 깨끗한 음성 이하, 글자 오류율은 그 이상으로 본다. 근거는 whisper-ko-ft 4단계(전화 대역·μ-law만으로 +1.9%p)에 15 dB 소음과 2% 손실을 더한 것이다. τ-Voice의 pass@1 하락(제공자별 5~14%p)은 다른 지표라 참고로만 둔다
- 100 ms씩 무음이 된 구간과 소음에서, VAD를 끈 인식기가 없는 말을 지어낼 수 있다. 그것도 열화의 효과로 센다

### 읽는 법 (재기 전에 적음)
- 열화한 음성의 이름 생존율은 V4의 `verify_caller`가 받아쓰기 한 번으로 이름을 맞출 수 있는 발화의 비율이다. 에이전트는 이름이 맞지 않으면 다시 물을 수 있으므로(9단계에서 23개 에피소드를 그렇게 되찾았다) 본인 확인 성공률과 같지 않다. 그것은 B단계의 몫이다
- 한 화자의 합성 음성에 생성 소음을 더한 것이다. 실제 통화(사람마다 다른 발음, 실제 소음, 코덱의 변형, 메움이 있는 손실)와 다르다. 이 결과는 "실제 통화 성능"이 아니라 "같은 합성 음성에 공개된 표준 열화 구성을 얹었을 때 인식이 잃는 몫"이다
- τ-Voice의 값은 영어 실시간 음성 에이전트를 위해 정한 것이다

### B단계(에피소드)는 이번에 열지 않는다
- B단계(개발용 24과제 × 4회를 열화한 채널로 다시 돌려 9단계 V4와 짝짓기. 1차 본인 확인, 2차 pass^1)는 이번 GPU 예산 밖이다. 9단계 V4 개발용 본인 확인(80.2%)은 바닥이 아니므로 판정자 계획의 조건은 맞지만, 열 때 따로 규칙을 적어 커밋한 뒤 잰다. A단계 결과를 보고 열화의 값을 바꾸지 않는다
- B단계를 열려면 실행기(`run.py`)의 채널에 열화를 붙이는 코드가 더 필요하다 (이번에는 만들지 않았다)

### 예상 GPU 시간 (상한 2시간)
