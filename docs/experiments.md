# 측정 규칙과 결과

규칙은 재기 전에 적고 커밋한다. 결과는 같은 절 아래에 덧붙인다. 규칙을 바꾸면 바꾼 시점과 이유를 남긴다.

## 공통 규칙 (2026-09-19, 측정 전)

### 판정
- 성공 = (1) 에피소드가 끝난 DB 덤프가 "새 복사본에 정답 동작만 실행한 덤프"와 같고 (2) 꼭 전달해야 하는 값이 고객에게 전달된 상담원 발화에 있다. LLM 판정은 쓰지 않는다. 원 τ-bench 논문의 방식(행동 결과 × 전달 정보)이다
- 비교에서 빼는 컬럼은 `db.IGNORED_COLUMNS`뿐이다: 티켓 본문, 이관 요약, 이관 사유, 이관 행의 고객 번호 (규정이 본인 확인 전후 어느 쪽의 이관도 허용하므로)
- 성공 조건에 "정답에 없는 쓰기가 0건"은 넣지 않는다 (τ-bench와 같다. 바꿨다가 되돌린 쓰기는 DB가 같으면 성공이다). 대신 성공했지만 정답에 없는 쓰기가 있었던 건수를 함께 보고한다
- 전달 값 검사: 숫자는 숫자 사이의 쉼표만 지운 뒤 앞뒤가 숫자·영문자·`-`·`.`이 아닌 위치에서 찾는다. 날짜는 월·일이 같고 연도가 없거나 같으면 일치. 글자는 NFKC·소문자·공백 제거 뒤 부분 문자열. 한글 수 표기("3만 2천 원")는 인식하지 않는다
- 고객의 종료 토큰은 `### stop ###`처럼 조금 다르게 써도 인정한다. 토큰과 함께 온 말("네, 진행해 주세요 ###STOP###")은 버리지 않고 에이전트에게 전달해 한 번 답하게 한 뒤 끝낸다. 시뮬레이터의 버릇이 에이전트의 실패로 세어지지 않게 하기 위해서다
- 판정하는 종료는 고객의 종료(`user_stop`), 시나리오 밖(`out_of_scope`), 이관(`handoff`)이다. 한도 초과와 형식 오류 종료는 실패로 센다. 제공자 오류, 시뮬레이터의 빈 응답, 도구 코드의 버그는 `infra_error`로 기록하고 분모에서 뺀다. 공식 실행에서 `infra_error`가 나오면 건수를 결과에 적는다

### 에이전트 루프
- 텍스트와 도구 호출이 함께 오면 도구 호출을 따르고 텍스트는 고객에게 보내지 않는다 (τ-bench v1과 같은 관대한 쪽)
- 도구 호출이 여러 개면 첫 번째만 실행한다
- 형식 오류(빈 응답, 본문에 샌 도구 호출, 길이 제한으로 잘림)는 고객에게 보내지 않고, 하니스 안내문을 넣어 한 턴에 2번까지 다시 시킨다. 넘으면 실패. 본문에 샌 도구 호출은 찾아내기만 하고(태그, 또는 본문 속 `name`+`arguments` JSON) 구제 실행하지 않는다. 형식 오류 수와 재시도 수를 결과와 함께 보고한다
- 한도: 에이전트 LLM 호출 30, 고객 턴 20, 도구 오류 10. 프롬프트가 `num_ctx`의 95%를 넘으면 종료
- 본인 확인은 실험 축이 아니다. 모든 조건에서 도구가 막고, 막힌 횟수를 센다

### 도구와 규정
- 읽기 도구는 사실만 돌려준다. "반품 가능 여부"나 "반품 기한" 같은 계산된 판단은 주지 않는다 (주면 P0와 P1의 차이를 도구 출력이 메운다)
- 도구 오류 메시지에는 이유만 적고 다음 행동 힌트를 넣지 않는다
- P0와 P1의 시스템 프롬프트와 규정 문서는 같다. 다른 것은 도구의 규정 검사 동작뿐이다
- 정답 재실행과 과제 검증은 항상 P1로 돌린다

### 과제
- 과제는 `seed.py`의 고정 행만 참조한다. 과제의 `now`는 seed의 모든 시각보다 뒤다 (쿠폰 만료 시각은 예외)
- 쓰기 인자를 결정하는 모든 선택(사유, 대상 줄, 교환할 옵션, 주소)은 시나리오의 `known`에 적는다. 시뮬레이터가 고를 여지를 두지 않는다
- 전달 값은 도구 결과에서만 알 수 있는 값으로 하고, 시나리오와 규정 문서에 나오는 값("7일" 등)이나 한두 자리 수는 쓰지 않는다. 과제 검증이 시나리오와 에이전트 시스템 프롬프트 전체를 검사한다 (2026-09-19 검토에서 규정 문서의 예시 날짜가 거절 과제의 전달 값과 같아, 조회 없이 예시만 말해도 통과하는 것을 찾아 고쳤다)
- 쓰기 대상 주문은 할인이 0원인 주문으로 한다 (반품 환불액의 할인 안분 규칙은 아직 없다)
- 여러 줄 반품은 한 번에 접수하는 것이 규정이다 (나눠 접수하면 반품 배송비가 두 번 빠져 DB가 달라진다)
- 한 과제에서 같은 부모 아래 새로 생기는 행은 1개까지
- 측정을 시작한 과제는 고치지 않는다. 고치면 시점과 이유를 적고 그 과제를 다시 잰다
- 개발용 과제로 프롬프트와 가드를 고치고, 시험용 과제는 단계가 끝날 때 고른 후보만 한 번 잰다. 시험용 에피소드를 보면서 고치지 않는다

### 무작위성
- 에이전트 temperature 0.0, 시뮬레이터 0.7. LLM 호출마다 seed = sha256(기준 seed, 과제, 시도, 역할, 호출 번호). temperature 0에서는 seed가 의미가 없고, 시도마다 달라지는 것은 시뮬레이터의 말이다
- GPU 연산이라 비트 단위 재현은 약속하지 않는다

## 0단계: 스모크 (측정 아님)

`tasks/smoke.yaml`의 과제 5개를 실제 모델로 한 번씩 돌려 에피소드가 끝까지 돌고 판정이 나오는지, 에피소드당 시간이 얼마인지 본다. 수치를 결과로 쓰지 않는다. 이때 확인해 1단계 규칙에 반영할 것:

- 시스템 프롬프트(규정 + 도구)의 실제 토큰 수와 `num_ctx` 16384의 여유
- `prompt_eval_count`가 캐시된 토큰을 포함하는지 (컨텍스트 한도 감지가 의존)
- 에이전트와 시뮬레이터가 같은 모델을 번갈아 쓸 때의 프롬프트 재평가 시간
- 모델이 enum 코드 인자를 제대로 쓰는지, 형식 오류가 얼마나 나는지

### 결과
아직 돌리지 않았다 (GPU를 다른 작업이 쓰는 중).

## 1단계: 과제와 기준선 (규칙 2026-09-19, 측정 전)

### 과제 묶음
- `tasks/dev.yaml` 24개: 조회 6, 처리 8, 거절 6, 복합 4
- `tasks/test.yaml` 40개: 조회 8, 처리 14, 거절 10, 복합 8
- 두 묶음은 고객과 주문을 공유하지 않는다 (개발용 `C-91xx`/`O-91xxx`, 시험용 `C-92xx`/`O-92xxx`). 같은 종류의 규정을 다루되 금액, 날짜, 상품, 말투가 다르다
- 쓰기 도구(취소, 반품, 교환, 배송지 변경, 보상 쿠폰, 티켓, 이관)와 규정 검사 코드가 두 묶음 모두에 고르게 나온다. 거절 과제에는 기한 하루 전후 같은 경계 사례를 넣는다 (기한 마지막 날은 처리, 다음 날은 거절)
- 개발용으로 프롬프트와 가드를 고친다. 시험용은 단계가 끝날 때 고른 구성만 한 번 재고, 시험용 에피소드를 보면서 무언가를 고치지 않는다

### 기준선
- 구성: P0 · R0 · `qwen2.5:7b-instruct`, 시뮬레이터도 같은 모델. 과제마다 4번
- 재는 것: pass^1~pass^4(과제 단위 부트스트랩 95% 구간), 유형별 성공률, 정답에 없는 쓰기 수, P0에서 통과된 규정 위반 코드별 횟수, 본인 확인 전 접근이 막힌 횟수, 형식 오류 수, 종료 사유별 건수, 에피소드당 시간
- 판정은 없다. 뒤 단계의 비교 기준이 된다
- 실패 분류는 개발용 에피소드로만 한다: 본인 확인 누락, 규정 위반, 잘못된 인자, 고객 확인 없이 실행, 값 전달 누락, 중간에 멈춤, 시뮬레이터 탓
- 시뮬레이터 점검: 개발용 에피소드 20개를 무작위(고정 seed)로 뽑아 읽고, 시나리오에 없는 정보를 지어냄 / 일찍 포기함 / 상담원 역할을 함 / 틀린 확인 요청에 동의함을 센다

### 결과
아직 재지 않았다.
