# 서비스 (3단계)

평가에서 쓰는 에이전트 루프와 도구를 그대로 웹 채팅으로 돌린다. 달라지는 것은 DB가 남는다는 점(PostgreSQL), 대화가 요청 사이에 저장된다는 점, 큰 환불은 사람이 승인한다는 점이다.

## 실행

모델은 호스트의 Ollama가 돌린다 (GPU가 필요해서 컨테이너에 넣지 않았다).

```bash
ollama pull qwen3.5:4b
docker compose up --build
```

- 에이전트 모델은 `qwen3.5:4b`, 비사고 모드다 (2026-10-04부터. 그 전에는 `qwen2.5:7b-instruct`). 이유와 알려진 위험은 아래 "정한 것과 이유"의 첫 항목

- 채팅: http://127.0.0.1:8062
- 관리 화면: http://127.0.0.1:8062/admin (토큰은 `ADMIN_TOKEN`, 기본값 `local-admin`)
- DB: `127.0.0.1:55462` (PostgreSQL 16)
- 포트는 모두 127.0.0.1에만 연다. 기본 비밀번호와 토큰은 로컬 시연용이다. 바꾸려면 `.env.example`을 `.env`로 복사해 값을 넣는다. DB 비밀번호는 앱의 DB 주소에 그대로 들어가므로 영문·숫자와 `- _ . ~`만 쓴다 (`@`나 `%`가 들어가면 주소가 잘못 읽혀 앱이 DB에 붙지 못한다)
- 처음 뜰 때 마이그레이션(Alembic)을 돌리고, 쇼핑몰 테이블이 비어 있으면 평가와 같은 생성 데이터를 넣는다. 채팅 화면 아래에 시험해 볼 고객 이름과 전화번호가 나온다

Docker 없이 SQLite 파일로도 돈다.

```bash
uv run uvicorn support_agent.service.app:create_app --factory --port 8062
```

설정은 환경 변수로 한다 (`SUPPORT_AGENT_` 접두사, `service/settings.py`): `DATABASE_URL`, `OLLAMA_URL`, `MODEL`, `THINK`, `POLICY`, `CLAIMS`, `NOW`, `APPROVAL_REFUND_WON`, `ADMIN_TOKEN`, `MAX_MESSAGE_CHARS`, `MAX_AGENT_CALLS_PER_TURN`, `MAX_TURNS_PER_SESSION`, `VOICE`, `TTS_DEVICE`, `STT_DEVICE`, `MAX_AUDIO_BYTES`, `MAX_TTS_CHARS`.

## 구성

```
브라우저 ── POST /api/sessions/{id}/messages (SSE) ──> app.py ──> core.ChatService.handle()
                                                                    │  agent.agent_turn()   평가와 같은 루프
                                                                    │  toolkit.execute()    평가와 같은 도구, 같은 단일 경로
                                                                    │    └ before_write = 승인 관문
                                                                    ▼
                                         PostgreSQL: 쇼핑몰 테이블 13개 + chat_sessions, audit_events, approvals
```

| 파일 | 하는 일 |
|---|---|
| `service/settings.py` | 환경 변수 설정 |
| `service/store.py` | 서비스 테이블 3개. 쇼핑몰 테이블과 메타데이터를 나눠서 판정용 덤프(`db.dump_db`)에는 들어가지 않는다 |
| `service/bootstrap.py` | 엔진 생성, Alembic 마이그레이션, 빈 DB에 생성 데이터 복사 |
| `service/core.py` | 한 턴 처리, 감사 로그, 승인 대기열. 웹 코드가 없어 테스트가 직접 부른다 |
| `service/app.py` | FastAPI: SSE 채팅, 관리자 API, 정적 화면 |
| `service/migrations/` | Alembic. 테스트가 "마이그레이션 결과 = 선언한 테이블"을 확인한다 |

## 테스트

- `tests/test_service.py`, `tests/test_review_t7.py`: 마이그레이션한 SQLite 파일과 대본대로 답하는 가짜 모델로 채팅, 승인, 감사 로그, 음성 끝점을 확인한다
- `tests/test_postgres.py`: PostgreSQL에서만 달라지는 곳을 확인한다. 마이그레이션 결과가 선언한 테이블과 같은지, 복사한 쇼핑몰 데이터가 생성 데이터와 시각까지 같은지, 감사 행을 쓰지 못하면 주문도 바뀌지 않는지, 두 프로세스가 같은 승인을 동시에 결정하면 한쪽만 실행하는지. `SUPPORT_AGENT_TEST_PG_URL`이 있을 때만 돌고(`docker compose up -d db` 뒤 `postgresql+psycopg://support:support-local@127.0.0.1:55462/support`), 그 서버에 `support_agent_test` 데이터베이스를 따로 만들어 쓴다. CI는 PostgreSQL 서비스 컨테이너를 띄워 이 테스트까지 돌린다

## 모델 없이 띄우기, 보안 스캔

```bash
uv run uvicorn support_agent.service.offline:create_offline_app --factory --port 8062
```

- `service/offline.py`는 모델 자리에 규칙 몇 줄짜리 대역을 넣는다 (이름과 전화번호를 보면 본인 확인, 주문 번호를 보면 조회, "취소"가 있으면 취소). 나머지는 실제 코드 그대로라 화면 작업, 웹 계층의 보안 스캔, 스모크 테스트를 GPU 없이 할 수 있다. `SUPPORT_AGENT_VOICE=1`이면 음성 끝점도 음성 모델 없는 대역으로 응답한다
- API 설명(`/openapi.json`)은 `SUPPORT_AGENT_EXPOSE_OPENAPI=1`일 때만 내놓는다. 스캐너가 경로와 본문 형태를 정확히 알게 하려는 것이고, 평소에는 꺼 둔다
- HawkScan(StackHawk) 설정은 `stackhawk.yml`이다. 비밀값은 없고 `APP_ID`, `ADMIN_TOKEN`, `SCAN_SESSION_ID`를 환경 변수로 받는다. 관리자 API는 `X-Admin-Token` 헤더를 미리 넣어 주는 방식으로 인증하고, 스캐너가 지어낸 세션 번호로는 "없는 세션"(404)에서 끝나므로 스캔 전에 만든 실제 세션 번호와 승인 번호를 `customVariables`로 넣어 준다

```bash
export SUPPORT_AGENT_EXPOSE_OPENAPI=1 SUPPORT_AGENT_VOICE=1 SUPPORT_AGENT_ADMIN_TOKEN=<임의의 토큰>
uv run uvicorn support_agent.service.offline:create_offline_app --factory --port 8062
# 다른 창에서: 세션을 하나 만들고(POST /api/sessions) 큰 금액 취소를 요청해 승인 대기를 하나 만든 뒤
APP_ID=<앱 번호> ADMIN_TOKEN=<같은 토큰> SCAN_SESSION_ID=<세션 번호> hawk scan
```

- **2026-10-05부터는 OWASP ZAP(무료, Apache-2.0)으로 스캔한다.** HawkScan은 체험 기간이 이날 끝났다. 설정은 `zap/automation.yaml`로 같은 스캔이다 (API 설명, 스파이더, 패시브 스캔, 기본 정책의 액티브 스캔). ZAP 2.17.0 공식 크로스플랫폼 패키지를 Java 17 이상으로 직접 돌린다 (Docker 없음). 관리자 토큰은 ZAP이 대상 호스트로 가는 모든 요청에 헤더를 붙이게 하는 환경 변수(`ZAP_AUTH_HEADER*`, `zap/run_zap.sh`가 정함)로 넘기고, 실제 세션·승인 번호는 `requestor` 작업이 그 번호로 요청을 한 번씩 보내 스캔 대상에 넣는다 (HawkScan의 `customVariables` 자리. 승인 결정 요청은 그 승인을 실행한다). 두 도구는 규칙 목록과 기본 설정이 달라 **결과를 직접 비교하지 않고, 같은 도구의 기록끼리만 비교한다**

```bash
# 위와 같이 오프라인 앱을 띄우고 세션과 승인 대기를 만든 뒤. ZAP_DIR은 zap-2.17.0.jar가 있는 폴더, 결과는 work/zap/<이름>/
ZAP_DIR=<폴더> ADMIN_TOKEN=<같은 토큰> SCAN_SESSION_ID=<세션 번호> SCAN_APPROVAL_ID=<승인 번호의 숫자> bash zap/run_zap.sh <이름>
```

## 정한 것과 이유

- **기본 모델은 `qwen3.5:4b`, 비사고 모드다 (2026-10-04부터).** 8단계 측정(`experiments.md` 8단계)에서 서비스 구성(P1) 그대로 에이전트 모델만 바꿨을 때 시험용 40과제 × 4회의 pass^1이 18.1%(qwen2.5 7B)에서 55.6%로 올랐다 (+37.5%p [+28.7, +46.2]). 7B가 0%였던 복합 과제가 31.2%가 됐고, 도구 호출을 본문에 쓰는 형식 오류는 84 → 0, 한자가 섞인 답은 2.9% → 0.4%다. 에이전트 호출당 시간은 1.24배(559 → 693 ms)다. 측정 규칙은 그 단계에서 서비스를 바꾸지 않게 정해 두었고, 결과표를 보고 사용자가 2026-10-04에 바꾸기로 정했다
  - **알려진 위험**: 시험용 과제에서 새 모델은 과제가 요구하지 않은 쓰기를 **13건** 했다. 이전 서비스 구성(qwen2.5 7B, P1)은 **6건**이었다. 새 모델은 훨씬 자주 행동해서(성공한 쓰기 27 → 100건) 쓰기 정밀도는 78% → 87%로 올랐지만, 잘못된 쓰기의 건수는 두 배다. 통과된 규정 위반은 두 구성 모두 0건이다 (도구가 막는다). 13건은 도구의 규정 검사를 통과한, 과제가 요구하지 않은 쓰기다. 큰 환불의 사람 승인(아래)은 그대로 켜 두지만 **이 13건에는 안전장치가 되지 못한다**: 시험용 기록을 다시 세어 보면 13건 모두 환불액이 10만 원 미만(가장 큰 것 83,500원)이거나 환불이 없는 쓰기(교환, 보상 쿠폰, 티켓, 상담원 연결)라 승인 관문에 걸리는 것이 0건이다. 승인 관문이 잡는 것은 환불액 10만 원 이상인 취소·반품뿐이라, 그보다 작은 환불과 다른 쓰기(교환, 배송지 변경, 보상 쿠폰, 상담 티켓)의 잘못된 처리는 막지 못하고 감사 로그에 남는다
  - `THINK`는 Ollama 요청의 `think` 값이다 (`on`, `off`, `omit` = 보내지 않음). 비워 두면 기본 모델에는 `off`(잰 그대로), 다른 모델에는 `omit`이다. 사고 모드가 없는 모델은 이 값을 거부할 수 있어서다. 이전 모델로 돌아가려면 `MODEL=qwen2.5:7b-instruct`만 바꾸면 된다 (Compose는 `.env`의 `MODEL`). 사고 모드가 있는 다른 모델을 쓰면 `THINK=off`를 함께 준다
  - 잰 구성과 다른 점: 서비스의 `num_ctx`는 16384다 (8단계는 12288로 쟀다. num_ctx는 KV 캐시의 크기와 대화가 닫히는 한도를 정한다). 고객이 시뮬레이터가 아니라 사람이고, 언어 가드(L1)가 켜져 있다. 음성 모드(V2 규칙)와 완료 주장 가드(C1)는 이 모델로 재지 않았다 (5단계·7단계는 qwen2.5 7B로 쟀다)
- **도구가 규정을 막는다 (P1).** 2단계 측정에서 P1은 성공률을 올리지 못했지만 통과된 규정 위반을 12건에서 0건으로 줄였다. 서비스에서 잘못된 환불은 돈이 나가는 일이라, 코드로 확인할 수 있는 규정은 모델을 믿지 않고 도구에서 막는다.
- **한국어가 아닌 답은 고객에게 보내지 않는다.** qwen2.5는 한국어 대화 도중에 중국어로 넘어가는 일이 있다 (개발용 기록에서 7B는 답 1,083개 중 12개, 14B는 801개 중 24개. 서비스를 실제 모델로 확인할 때도 나왔다. 2026-10-04부터의 기본 모델 qwen3.5 4B는 8단계 시험용 기록에서 답 1,667개 중 7개). 서비스는 한자나 가나가 두 글자 이상 든 답을 형식 오류처럼 돌려보내고 한국어로 다시 답하게 한다 (`RunConfig.language = "L1"`). 재시도를 다 쓰고도 안 되면 정해진 한국어 안내 문장이 나간다. 이 가드는 측정하지 않았다. 평가의 기본값은 끈 상태(`L0`)다
- **완료 주장 가드는 설정이다 (`CLAIMS`, 기본 `C0`).** 켜면 "취소가 완료되었습니다"처럼 끝났다고 말하는 답을 그 대화의 성공한 도구 결과(승인 대기열에 올라간 요청은 "접수되었다"는 말의 근거)와 대조하고, 근거가 없으면 고객에게 보내지 않고 다시 시킨다. 개발용 측정에서 기본값으로 켜는 조건에 들지 못해 꺼 두었다 (`experiments.md` 7단계). 7단계는 qwen2.5 7B로 쟀고, 2026-10-04부터의 기본 모델(qwen3.5 4B)로는 재지 않았다. 승인이 실행되면 그 결과가 대화에 도구 결과로 남으므로, 그 뒤의 "처리되었습니다"는 근거가 있다
- **응답은 이벤트 단위로 흘린다.** 글자 단위가 아니다. 에이전트의 응답은 고객에게 가기 전에 검사를 거친다(도구 호출이 본문에 샌 응답, 잘린 응답은 전달하지 않고 다시 시킨다). 글자를 먼저 흘리면 이 검사를 할 수 없다. 대신 도구를 부를 때마다 "주문 조회 중" 같은 진행 이벤트를 보낸다. 이벤트: `status`, `tool`, `tool_result`, `approval`, `error`, `reply`, `end`.
- **브라우저가 끊겨도 턴은 끝까지 간다.** 도구가 DB를 바꿨는데 대화 기록이 없는 상태를 만들지 않기 위해서다.
- **사람 승인.** 환불액이 기준(기본 10만 원) 이상인 취소·반품은 바로 실행하지 않는다. 환불액은 도구의 규정 계산이 끝나야 알 수 있으므로, 관문은 도구의 트랜잭션 안에 있다: 핸들러가 계산한 실제 `refund_won`이 기준 이상이면 그 트랜잭션을 롤백하고 승인 대기열에 올린 뒤 에이전트에게 `approval_required` 오류로 알린다. 미리 계산해 보는 단계가 따로 없으므로 "확인할 때는 기준 아래였는데 실행할 때는 위"인 틈이 없다. 같은 요청을 다시 호출해도 대기열에는 하나만 남는다.
  - 반품은 같은 주문에 이미 접수된 반품의 환불액을 더해 기준과 비교한다. 줄을 한 번에 하나씩 나눠 접수해도 합계가 기준에 닿는 반품부터는 사람이 승인한다. 합계가 이미 기준 이상인 주문은 앞의 반품이 승인을 거쳤더라도 그 뒤의 반품도 모두 사람에게 간다. 승인하면 그 호출의 환불액만 처리된다.
  - 승인하면 그때 도구를 실행한다. 그 사이 주문 상태가 바뀌어 도구가 거절하면 `failed`로 남는다.
  - **승인 대기에 걸린 턴의 답은 서비스가 정해진 문장으로 쓴다 (2026-10-05부터).** 예: "주문 O-10097의 취소 요청(환불 예정 108,200원)은 담당자 승인이 필요해 아직 처리되지 않았습니다. 승인 번호는 AP-1이며, 담당자가 확인한 뒤 결과를 이 대화창으로 안내해 드립니다." 에이전트가 읽는 도구 결과(`approval_required`)는 그대로이고, 거기에는 에이전트에게만 하는 지시("고객에게 …라고 알리세요", "같은 요청을 다시 호출하지 마세요")가 들어 있다. 실제 모델이 이 지시를 고객에게 거의 그대로 옮긴 일이 있어서(아래 "qwen2.5 7B로 써 보면"의 큰 취소), 그 턴의 모델 답은 고객에게 보내지 않는다. 대화 기록에는 전달되지 않은 답으로(`delivered: false`, 평가 기록과 같은 표시), 감사 로그의 `agent_reply`에는 `not_delivered`로 남는다. 같은 턴에 다른 쓰기가 실행됐으면(한 주문의 반품 두 줄 가운데 한 줄만 승인에 걸린 경우 등) 그 일을 알리는 것은 모델의 답뿐이라, 모델 답에서 지시를 옮긴 문장(공백을 빼고 지시와 10글자 이상 이어서 같거나 "호출"이 든 문장)만 빼고 정해진 문장 앞에 붙인다. 이 경우에는 지시를 다른 말로 바꿔 옮긴 문장이 걸러지지 않을 수 있다
  - 이렇게 한 이유: 평가가 잰 것을 바꾸지 않기 위해서다. 승인 관문은 서비스에만 있고 평가에는 없다 (평가의 도구는 10만 원 이상 취소도 바로 실행한다). 에이전트 루프(`agent.py`)도, 모델이 받는 도구 결과 문구도 바이트까지 그대로라(테스트가 문구를 고정한다) 서비스의 모델이 받는 입력과 완료 주장 가드가 근거로 읽는 형식(`claims.py`)이 바뀌지 않는다. 바뀌는 것은 고객에게 보내는 글뿐이다. 모델에게 주는 문구에서 지시를 빼는 방법은 모델의 입력을 바꾸고, 그래도 모델이 다른 문장을 옮길 수 있다. 모델 답에서 지시 문장만 거르는 방법은 말을 바꾸면 빠져나가므로, 거르기는 다른 쓰기의 결과를 알려야 하는 턴에만 쓴다
  - 승인은 조건부 UPDATE 한 번으로 선점한다(`pending` → `executing`). 두 담당자가, 또는 두 프로세스가 같은 승인을 동시에 눌러도 한쪽만 실행한다. 실행 중에 오류가 나면(감사 행을 쓰지 못함, DB 오류 등) 도구의 변경은 롤백되고 승인은 `pending`으로 돌아가 다시 결정할 수 있다 (관리 화면에는 "결정을 저장하지 못했습니다"가 뜨고 감사 로그에 오류가 남는다). 실행 중에 프로세스가 죽거나, 되돌릴 때 DB에 닿지 못하면 `executing`으로 남는다. 이때 쇼핑몰 데이터는 바뀌지 않았으므로(아래) 사람이 확인하고 다시 요청하면 된다
- **쇼핑몰 데이터의 변경과 감사 로그는 한 트랜잭션이다.** 도구가 성공하면 그 호출의 감사 행과, 승인 실행이면 승인의 `approved` 표시까지 도구의 변경과 함께 커밋되거나 함께 롤백된다 (`toolkit.execute`의 `on_success`). 감사 행 없이 주문만 바뀐 상태는 생기지 않는다. 대화 기록은 턴이 끝날 때 따로 저장하므로, 턴 도중 프로세스가 죽으면 대화에는 그 호출이 없고 감사 로그에는 있다. 고객이 다시 요청하면 도구가 이미 처리된 주문이라고 거절한다
  - 결과는 정해진 문장으로 대화에 들어간다 (모델이 쓰지 않는다). 고객 화면은 5초마다 대화를 다시 읽어 보여 준다.
- **감사 로그는 추가만 한다.** 고객 메시지, LLM 호출(토큰 수·시간·형식 오류), 도구 호출(인자, 결과, 쓰기 여부, 본인 확인된 고객), 응답, 승인 요청과 결정이 한 줄씩 남는다. 거절된 도구 호출은 바뀐 것이 없으므로 따로 적는다.
- **세션 id가 곧 열쇠다.** 고객 쪽에는 로그인이 없다. 본인 확인은 평가와 같이 `find_customer`(이름 + 연락처)로 하고, 확인된 고객 번호는 세션에 저장된다. 세션 id는 추측할 수 없는 난수다.
- **고정 시계.** 생성 데이터는 2026-09-14 10:00(KST) 무렵에 맞춰져 있다. 실제 시계를 쓰면 곧 모든 주문이 반품 기간을 넘기므로 시연은 이 시각에 고정한다. `SUPPORT_AGENT_NOW=real`이면 실제 시계를 쓴다. 고정되는 것은 도구와 규정이 보는 "쇼핑몰의 지금"뿐이고, 세션·감사 로그·승인 기록의 시각은 항상 실제 시각이다.
- **한 세션은 한 번에 메시지 하나.** 프로세스 안의 세션별 잠금으로 막는다. 그래서 앱은 프로세스 하나로 띄운다. 여러 프로세스로 늘리려면 이 잠금을 DB 행 잠금으로 바꿔야 한다.
- **한도.** 메시지 1,000자(설정으로 4,000자까지), 턴당 LLM 호출 12번과 실패한 도구 호출 10번(넘으면 그 턴은 고정 안내로 끝난다. 앞 턴들의 실패는 세지 않는다), 세션당 40턴, 동시에 도는 턴 4개(넘으면 503과 `Retry-After`). 컨텍스트가 차거나 40턴이 되면 세션을 닫고 새 상담을 권한다. 음성은 파일 5 MB와 풀었을 때 60초까지이고 (길이는 푸는 도중에 프레임마다, 16 kHz로 바꾸기 전에 센다. 몇 kB짜리 파일에 몇 시간의 무음이 들 수 있고 샘플레이트가 아주 낮으면 프레임 하나가 몇 시간이 되어서, 다 푼 뒤나 16 kHz로 바꾼 뒤에 재면 그 사이 메모리를 수백 MB~GB 쓴다), 인식된 문장이 메시지 한도를 넘으면 자르지 않고 다시 말해 달라고 한다 (문장 끝의 "취소하지 마세요"가 잘리면 뜻이 뒤집힌다).

## 음성

선택 기능이다. `SUPPORT_AGENT_VOICE=1`이면 마이크로 말하고 답을 소리로 들을 수 있다. 인식된 문장은 글로 보낸 메시지와 같은 길을 가므로 규정 검사, 사람 승인, 감사 로그가 그대로 적용된다. 설치와 끝점은 [voice.md](voice.md).

2026-10-04까지의 기본 모델 qwen2.5 7B는 측정한 그대로 움직인다. 개발용 과제의 20%만 끝까지 처리하고, 가장 흔한 실패는 "확인해 보겠습니다"만 하고 도구를 부르지 않는 것이다. 실제 모델로 서비스를 확인할 때도 주문 취소를 세 번 부탁하는 동안 같은 말만 되풀이했고, 조회 도구를 부르지 않고 주문 상태를 지어내기도 했다. 가장 나쁜 경우도 나왔다: `docker compose`로 띄운 서비스에서 주문 취소를 부탁하자 7B는 취소 도구를 한 번도 부르지 않은 채 "주문이 취소되었습니다. 12,000원이 환불되었습니다"라고 답했다. 주문은 DB에 결제 완료 그대로였고, 12,000원은 규정 문서의 예시에 나오는 금액이다. 도구가 규정을 막고 큰 환불은 사람이 승인하므로 잘못된 처리가 DB에 남지는 않지만, 하지 않은 일을 했다고 말하는 것은 막지 못한다. 평가에서는 이런 에피소드가 실패로 잡힌다 (최종 DB가 정답과 다르다). 그래서 "끝났다"는 답을 그 대화의 도구 결과와 대조해 근거가 없으면 돌려보내는 가드를 만들어 쟀다 (`experiments.md` 7단계). 거짓 완료의 전달은 0이 되지만 7B는 안내문을 받고도 도구를 부르지 않아 성공률이 오르지 않았고(C1 −2.1%p, 정답에 없는 쓰기 한 건 증가), 재기 전에 적은 조건에 걸려 기본값으로 켜지 않았다. `SUPPORT_AGENT_CLAIMS=C1`로 켤 수 있고, 켜면 세 번째에도 같은 주장을 하는 턴에는 "방금 요청을 처리하지 못했습니다"라는 고정 안내가 나간다. 14B는 성공률이 두 배쯤이고(`MODEL=qwen2.5:14b-instruct`) 이 PC에서는 호출당 몇 초가 걸린다.

새 기본 모델 `qwen3.5:4b`로는 2026-10-04에 서비스를 호스트에서 띄워(새 SQLite DB, 고정 시계, 기본 설정 그대로: P1, `think: false`, `/healthz`가 `"model":"qwen3.5:4b","think":"off"`) 실제 모델로 상담 두 개를 해 봤다. Ollama 0.35.1, RTX 2080 Ti, 끝날 때 모델은 100% GPU였다. 측정이 아니라 동작 확인이고(대화 둘), 시간은 GPU가 쉬지 않을 때(데스크톱 앱이 사용률 약 25%, 메모리 약 1.0~1.4 GiB) 본 참고값이다. 모델 없이 확인한 것(서비스가 보내는 모든 에이전트 요청에 `"model": "qwen3.5:4b"`와 `"think": false`가 들어가고, 이전 모델을 고르면 `think`를 보내지 않음. `tests/test_service.py`)은 그대로다.
- 작은 취소(정예준, O-90005, 89,100원): 첫 메시지에 이름·전화번호·주문 번호·요청을 함께 보내자 `find_customer` → `list_orders`를 부르고 "취소하시겠습니까?"라고 물었다. "네, 진행해 주세요"에 `cancel_order`를 불러 DB의 주문이 `cancelled`, 결제가 환불 대기 89,100원이 됐고, 답의 금액과 환불 수단(간편결제)이 DB와 같았다. 다만 동의를 묻기 전에 환불액을 말하지 않았다 (규정 3은 대상과 환불액을 말하고 동의를 받으라고 한다)
- 큰 취소(강정우, O-10097, 108,200원): 본인 확인 뒤 주문을 조회하지 않고 "취소하시겠습니까?"를 먼저 물었고, "네"에 `get_order`로 조회해 금액(108,200원)과 환불 수단(계좌이체)을 말하고 다시 물었다. 두 번째 "네"에 `cancel_order`가 승인 관문에 걸려 승인 대기 AP-1이 생기고 주문은 그대로였다. 이때의 답은 도구가 에이전트에게 돌려준 안내문(`service/core.py`의 `approval_required` 문구)을 거의 그대로 고객에게 옮겼다: "…담당자 확인 후 처리되며 결과는 이 대화창으로 안내된다고 알려드리겠습니다. 같은 요청을 다시 호출하지 마세요." 승인 번호는 말하지 않았다. 한 번 본 것이라 얼마나 자주 그러는지는 모르고, 고치지 않았다. **2026-10-05 고침** (`972317b`): 이제 승인 대기에 걸린 턴에 고객이 읽는 답은 서비스의 정해진 문장(주문, 금액, 승인 번호)이고 모델의 답은 전달하지 않는다 (위 "사람 승인". 이 대화를 대본으로 다시 재생하는 테스트가 `tests/test_service.py`에 있다. 모델 없는 오프라인 앱으로도 HTTP를 거쳐 확인했다: 대역은 도구 결과를 그대로 답으로 옮기는데, 고객에게는 정해진 문장이 갔고 지시가 든 대역의 답은 감사 로그의 `not_delivered`에만 남았다 (8차 스캔 준비). 실제 모델로 다시 확인하지는 않았다)
- 7B에서 본 멈춤("확인해 보겠습니다")과 도구 없이 끝났다고 말하는 답은 이 두 대화에서는 나오지 않았다. 에이전트 호출 11번 모두 형식 오류(언어 가드 포함) 0이고, 감사 로그에 호출마다 토큰(프롬프트 3,526~4,314)과 시간이 남았다. 첫 호출은 D: HDD에서 모델을 읽느라 55초, 그 뒤는 0.4~1.4초였다
- 하지 않은 것: Compose(PostgreSQL) 스택, 음성 모드, 승인 뒤의 대화, 여러 턴에 걸친 다른 업무(반품·교환 등)

## 하지 않은 것

- 요청 빈도 제한이 없다 (동시 실행 수만 막는다). 포트를 127.0.0.1에만 여는 것으로 대신했다. 밖에 내놓으려면 앞단에 프록시와 빈도 제한이 필요하다
- 같은 주문을 두 세션이 같은 순간에 바꾸는 경우는 DB 제약에 맡겼다 (늦은 쪽이 실패한다). 두 세션이 같은 주문의 다른 줄을 같은 순간에 반품하면 승인 기준의 합계도 서로를 보지 못한다. 합계는 주문별이라 다른 주문으로 나눈 반품은 따로 센다. 주문 행을 잠그려면 도구 코드를 고쳐야 하는데, 도구는 평가 대상이라 이 단계에서 건드리지 않았다
- 턴 전체의 제한 시간이 없다. 모델 호출 하나의 제한 시간(10분)과 턴당 호출 수만 있다
- 완료 주장 가드를 켠 경우, 같은 턴에 쓰기가 성공한 뒤 다른 종류의 일을 끝냈다고 세 번 말하면 고객은 "처리하지 못했습니다"를 듣는다 (DB는 바뀌어 있다). 검출은 정규식이라 목록에 없는 표현("성공했습니다", 관형형 "발급된")은 빠져나간다
- 관리자 인증은 공유 토큰 하나다. 담당자 이름은 입력한 대로 기록된다
- 상담원 연결(`transfer_to_human`) 뒤를 받는 화면은 없다. 세션이 `handoff`로 닫히고 관리 화면의 상담 기록에 남는다
