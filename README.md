# support-agent

한국어 고객센터 업무를 **도구 호출**로 처리하는 LLM 상담 에이전트와, 그 에이전트가 얼마나 믿을 만한지를 **미리 정한 규칙으로 재는 평가 환경**이다. 가상의 온라인 쇼핑몰 고객센터를 다룬다. 에이전트는 고객과 대화하면서 주문 조회, 취소, 반품·교환 접수, 배송지 변경, 보상 쿠폰 발급, 상담원 이관 같은 도구를 호출하고, 한국어 규정 문서를 지켜야 한다.

"데모에서 한 번 됐다"에서 끝내지 않고 다음을 수치로 남기는 것이 목적이다.

- 같은 과제를 여러 번 시켰을 때 몇 번 성공하는가 (pass^k)
- 규정을 어기는 일이 얼마나 있는가 (안 되는 환불을 해 주는 등)
- 규정을 프롬프트에만 적는 것과 도구 안에서도 막는 것은 얼마나 다른가
- 로컬에서 도는 4~14B 모델로 어디까지 되는가

계획은 [docs/plan.md](docs/plan.md), 설계는 [docs/design.md](docs/design.md), 측정 규칙과 결과는 [docs/experiments.md](docs/experiments.md), 서비스·MCP 서버·음성 채널은 [docs/service.md](docs/service.md)·[docs/mcp.md](docs/mcp.md)·[docs/voice.md](docs/voice.md).

## 평가 방식

[τ-bench](https://arxiv.org/abs/2406.12045) 논문의 방식을 따른다 (코드와 데이터는 가져오지 않았고, 도메인·규정·과제는 한국어로 새로 만들었다).

- 고객 역할은 시나리오를 받은 LLM(사용자 시뮬레이터)이 맡는다
- 에피소드마다 가상 DB의 복사본을 하나 만들어 쓴다
- 판정에 LLM을 쓰지 않는다. **끝난 뒤의 DB 상태가 "새 DB에 정답 동작만 실행한 상태"와 같고**, **꼭 전달해야 하는 값(환불 금액 등)을 고객에게 말했으면** 성공이다
- 거절해야 하는 과제는 DB가 그대로여야 하고, 도구로 조회해야만 알 수 있는 값을 말해야 한다. 아무것도 안 하고 규정만 읊는 에이전트, 상담원에게 떠넘기는 에이전트는 통과하지 못한다
- 과제 파일 자체도 테스트한다: 정답 동작이 실제로 실행되는지, 금지 동작이 규정 검사에 실제로 막히는지, 전달 값이 시나리오에 새어 있지 않은지

### 측정 결과 (2단계)

규칙을 먼저 적고 커밋한 뒤 개발용 과제로 고르고, 시험용 과제는 마지막에 한 번만 쟀다. 전체 기록은 [docs/experiments.md](docs/experiments.md), 에피소드별 원자료는 `reports/`.

| 구성 (개발용 24과제 × 4회) | pass^1 | 기준과의 차이 [95% 구간] | 정답에 없는 쓰기 | 통과된 규정 위반 |
|---|---|---|---|---|
| 기준: qwen2.5 7B, 규정은 프롬프트에만 | 20.8% | | 12 | 12 |
| 규정을 도구에서도 막음 | 15.6% | −5.2%p [−18.8, +7.3] | 2 | 0 |
| think 도구 | 13.5% | −7.3%p [−19.8, +3.1] | 12 | 7 |
| 멈춤 가드 | 11.5% | −9.4%p [−20.8, +0.0] | 14 | 12 |
| 본문에 샌 도구 호출 구제 | 17.7% | −3.1%p [−8.3, +1.0] | 16 | 14 |
| qwen2.5 14B | 47.9% | +27.1%p [+11.5, +42.7] | 18 | 11 |

- 7B에서 시도한 후보는 모두 기준을 넘지 못했다. 14B는 크게 올랐지만 미리 정한 채택 조건(호출당 시간 3배 이하, 정답에 없는 쓰기가 늘지 않음)에 걸려 채택하지 않았다. 그래서 **판정은 "개선 없음"**이고, 시험용 40과제의 기준 수치는 pass^1 16.2% [8.8, 24.4], pass^4 2.5%다. 판정과 무관한 참고 측정으로 14B를 시험용에 한 번 돌렸을 때는 34.8%(+18.5%p [+9.4, +27.9])였고, 규정을 어긴 쓰기도 함께 늘었다 (14 → 20건)
- 도구에서 규정을 막는 것은 성공률은 못 올렸지만 규정을 어긴 쓰기를 12건에서 0건으로 줄였다. 서비스(3단계)는 이 방식을 쓴다
- "확인해 보겠습니다"만 하고 멈추는 응답을 정확히 잡아 다시 시켜도 7B는 행동으로 옮기지 못했다. 멈춤은 출력 형식이 아니라 다음에 할 일을 모르는 문제로 보인다

### 측정 결과 (5단계: 음성 채널)

고객의 말을 말로 풀어 쓰고("O-91010" → "오 다시 구일공일공") 음성 합성과 음성 인식을 거친 뒤 에이전트에게 준다. 나머지는 기준 구성 그대로다. 규칙은 재기 전에 커밋했고, 정규화 규칙은 개발용 기록만 보고 만들었다.

| 시험용 40과제 × 4회 | pass^1 | 차이 [95% 구간] | 본인 확인까지 간 에피소드 | 주문 번호가 그대로 전달 | 이메일 | 전화번호 |
|---|---|---|---|---|---|---|
| 글 (V0) | 16.2% | | 73.1% | | | |
| 음성 채널 (V1) | 1.9% | V0보다 −14.4%p [−23.1, −6.9] | 20.6% | 0/594 | 0/540 | 76% |
| 음성 채널 + 정규화 (V2) | 8.8% | V1보다 +6.9%p [+1.9, +13.1] | 27.5% | 88% | 46% | 70% |

- 인식 결과의 글자 오류율은 7.6%인데 성공률은 8분의 1이 됐다. 틀린 글자가 도구 인자가 되는 값에 몰려 있기 때문이다. "오"가 숫자 5이기도 해서 "O-91010"은 매번 "5-91010"으로 적혔다
- 표기를 고치는 규칙 네 개(주문 번호의 O, 이메일의 골뱅이와 도메인, 전화번호 구분, 만 단위 금액)가 성공률의 절반쯤을 되찾았다. 개발용(+9.4%p)과 시험용(+6.9%p)에서 같은 방향이다
- 돌아오지 않는 것은 본인 확인이다. 전화번호의 빠진 숫자, 이메일의 빠진 철자, 비슷한 소리의 다른 이름은 표기가 아니라 소리에서 잃은 것이라 규칙으로 고칠 수 없다. 음성 상담의 본인 확인은 불러 주는 값을 받아 적는 것과 다른 수단이 필요하다
- 서비스를 실제 마이크로 써 보면 합성 음성에서는 없던 오류가 나온다. 말 없는 녹음이 "다음 영상에서 만나요."로 적히고, 사람이 부른 전화번호가 한글로 적힌다. 둘은 서비스에서 따로 고쳤다 ([docs/voice.md](docs/voice.md))

### 측정 결과 (7단계: 완료 주장 가드)

서비스를 실제 모델로 써 보니 7B가 취소 도구를 부르지 않은 채 "주문이 취소되었습니다"라고 답했다. 이런 답을 그 대화의 성공한 도구 결과와 대조해, 근거가 없으면 고객에게 보내지 않고 안내문을 넣어 다시 시키는 가드를 만들었다 (한 턴에 두 번, 그래도 같으면 전달하지 않고 끝낸다). 검출 규칙은 개발용 기록만 보고 만들었고, 판정 규칙은 재기 전에 커밋했다.

| 개발용 24과제 × 4회 | pass^1 | 기준과의 차이 [95% 구간] | 정답에 없는 쓰기 | 거짓 완료가 고객에게 전달된 응답 | 돌려보낸 응답 뒤 도구 호출 |
|---|---|---|---|---|---|
| 기준 | 19.8% | | 11 | 39 | |
| C1: 돌려보내고 다시 시킴 | 17.7% | −2.1%p [−8.3, +3.1] | 12 | 0 | 0 / 61 |
| C2: 다시 시킬 때 temperature 0.7 | 14.6% | −5.2%p [−9.4, −1.0] | 11 | 0 | 3 / 80 |

- 거짓 완료가 고객에게 가는 것은 막지만 성공률은 오르지 않는다. 7B는 "도구 결과에 기록이 없다, 지금 이 도구를 호출하라"는 안내문을 받고도 같은 주장을 되풀이하거나 "처리 중입니다"로 바꿀 뿐 도구를 부르지 않는다 (2단계의 멈춤 가드와 같은 결론). 다시 시킬 때 temperature를 올리면 더 나빠지고, 그때 나온 도구 호출 두 건은 둘 다 정답에 없는 쓰기였다
- **판정: 개선 없음.** 채택 조건(+5%p)에 든 후보가 없어 시험용은 재지 않았다. 서비스 기본값도 재기 전에 적은 조건(−5%p 안쪽이고 정답에 없는 쓰기가 늘지 않음)을 C1은 쓰기 한 건 차이로, C2는 성공률로 어기므로 켜지 않고 설정(`SUPPORT_AGENT_CLAIMS=C1`)으로만 남겼다. 켤지는 이 표를 보고 정하면 된다

### 측정 결과 (8단계: 새 세대 소형 모델)

지금까지 성공률을 움직인 것은 모델 크기뿐이었고, 14B는 GPU에 다 올라가지 않아 느렸다. 그래서 서비스 구성(규정을 도구에서도 막음, P1)에서 에이전트 모델만 2025~2026년에 나온 4B 모델로 바꿔 쟀다. 시뮬레이터(qwen2.5 7B)와 과제·규정·프롬프트는 그대로이고, 두 모델 모두 시뮬레이터와 함께 GPU에 올라갔다. 공유 설치인 Ollama가 0.35로 바뀌어 기준도 같은 버전(0.35.1)에서 다시 쟀다. 규칙(쓰기 조건은 위반이 통과되지 않고 정답에 없는 쓰기가 P0·7B 참조 이하)은 재기 전에 커밋했다.

| 개발용 24과제 × 4회 (P1) | pass^1 | 기준과의 차이 [95% 구간] | pass^4 | 정답에 없는 쓰기 | 형식 오류 | 에이전트 호출당 |
|---|---|---|---|---|---|---|
| 기준: qwen2.5 7B | 15.6% | | 4.2% | 2 | 48 | 587 ms |
| `qwen3:4b-instruct-2507` | 44.8% | +29.2%p [+15.6, +43.8] | 20.8% | 4 | 0 | 569 ms |
| `qwen3.5:4b` (비사고 모드) | 58.3% | +42.7%p [+29.2, +56.2] | 29.2% | 3 | 0 | 714 ms |

| 시험용 40과제 × 4회 | pass^1 | 기준과의 차이 [95% 구간] | pass^4 | 정답에 없는 쓰기 | 통과된 규정 위반 | 한자 섞인 답 |
|---|---|---|---|---|---|---|
| 기준: qwen2.5 7B, P1 | 18.1% | | 2.5% | 6 | 0 | 2.9% |
| 참조: qwen2.5 7B, P0 (규정은 프롬프트에만) | 15.6% | | 2.5% | 19 | 14 | 2.3% |
| `qwen3.5:4b`, P1 | **55.6%** | **+37.5%p [+28.7, +46.2]** | 20.0% | 13 | 0 | 0.4% |

- **판정: 개선.** 구간이 0보다 위이고, 정답에 없는 쓰기(13)가 P0·7B 참조(19) 이하다. 조회·처리·거절·복합 네 유형이 모두 올랐고, 7B가 0%였던 복합 과제가 31.2%가 됐다. 도구 호출을 본문에 쓰는 형식 오류는 84 → 0이다
- 재기 전에 적은 규칙대로 이 단계에서는 서비스의 기본 모델을 바꾸지 않았다. 이 표를 보고 **2026-10-04에 서비스의 기본 모델을 `qwen3.5:4b`(비사고 모드)로 바꿨다.** 시험용 pass^1이 세 배이고(18.1% → 55.6%), 형식 오류(도구 호출을 본문에 씀)가 84 → 0, 한자가 섞인 답이 2.9% → 0.4%로 줄었기 때문이다. `SUPPORT_AGENT_MODEL=qwen2.5:7b-instruct`로 이전 모델로 돌아갈 수 있다
- **알려진 위험**: 시험용 과제에서 새 모델은 과제가 요구하지 않은 쓰기를 13건 했다. 이전 서비스 구성(qwen2.5 7B, P1)은 6건이었다. 성공한 쓰기가 27 → 100으로 늘어 쓰기 정밀도는 78% → 87%로 올랐지만, 잘못된 쓰기의 건수는 두 배다. 큰 환불(10만 원 이상)의 사람 승인은 그대로 켜 두지만, 이 위험의 안전장치는 되지 못한다: 13건 모두 환불액이 10만 원 미만(가장 큰 것 83,500원)이거나 환불이 없는 쓰기(교환, 보상 쿠폰, 티켓, 상담원 연결)라 승인 관문에 걸렸을 것이 0건이다. 잘못된 쓰기는 감사 로그로 사후에 찾을 수 있을 뿐이다 ([docs/service.md](docs/service.md))
- 시뮬레이터를 다시 점검했다(구성 이름을 가린 두 장으로 개발용 60개를 읽음). 결과를 바꿨을 만한 시뮬레이터 잘못은 20개 중 7B 4개, qwen3 4B 6개, qwen3.5 4B 3개다. 20개씩이라 이 차이는 잡음 안이고, 강한 에이전트에서 시뮬레이터 잘못이 결과를 더 좌우하는지는 이 크기로 가를 수 없다. qwen3.5 4B 몫은 7B 에피소드를 공유한 둘째 장이라 사실상 가려지지 않은 채 읽었다 (`docs/experiments.md` 8단계 날짜 메모)

### 측정 결과 (9단계: 음성 V4, 개발용만)

5단계에서 음성 상담은 본인 확인에서 무너졌다 (받아 적은 연락처가 틀림). V4는 연락처를 받아 적는 대신 전화가 온 번호의 고객 한 명과 이름만 맞춘다. 에이전트 `qwen3.5:4b`, 시뮬레이터 qwen2.5 7B(층 일부를 CPU에), 규정은 프롬프트에만(P0), 같은 합성·인식 채널로 V2와 짝지어 쟀다. 결과는 음성 인식이 나아진 것이 아니라 **설계 변경의 효과**다.

| 개발용 24과제 × 4회 | 본인 확인 성공 | V2와의 차이 [95% 구간] | pass^1 | V2와의 차이 [95% 구간] | 정답에 없는 쓰기 | 통과된 규정 위반 |
|---|---|---|---|---|---|---|
| V2: 받아 적은 이름과 연락처 | 53.1% | | 35.4% | | 7 | 2 |
| V4: 발신 번호 + 이름 정확히 | **80.2%** | **+27.1%p [+11.5, +43.8]** | 51.0% | +15.6%p [+3.1, +28.1] | 23 | 9 |

- **판정 없음.** 개발용 결과가 시험용으로 가는 조건을 만족했지만, 시험용 두 실행이 GPU 시간 상한(8시간) 안에 들지 않아 재지 않았다. 개발용 결과는 시험용 판정을 대신하지 않는다
- V2의 실패한 확인은 대부분 받아 적은 값으로 고객을 찾지 못한 것이다 (189번 중 19번은 연락처 자리에 주문 번호나 빈 값·"모름"을, 또는 이름 자리에 "전기 그릴 고객" 같은 말을 넣은 호출이다). V4의 실패 48번은 한 번(이름 자리에 주문 번호)을 빼면 모두 이름이 한 글자라도 다르게 들린 것이다. 4B 에이전트는 이름이 맞지 않으면 다시 불러 23개 에피소드를 되찾았다
- 본인 확인이 늘자 정답에 없는 쓰기(7 → 23)와 통과된 규정 위반(2 → 9, 반품·교환 기간 등)도 늘었다. 23건 가운데 9건이 통과된 규정 위반이고, 서비스 구성(P1)이었다면 도구가 이 9건을 거절했을 것이다. 나머지 14건은 규정 위반이 아닌 쓰기(상담원 연결 6, 기한 안의 반품 5, 티켓 2, 주문 취소 1)라 P1에서도 막히지 않는다. 서비스 구성으로 V4를 잰 기록은 없다
- 두 LLM과 음성 모델이 11 GB GPU에 다 들어가지 않아 시뮬레이터 층 일부를 CPU로 옮겼고, 그래도 카드가 넘쳐 V4 실행 한 번이 음성 모델의 메모리 부족으로 멈춰 다시 쟀다 (`docs/experiments.md` 9단계 측정 중 메모)

### 측정 결과 (11단계: 전화 통화 조건에서 인식만, 판정 없음)

9단계 V4 개발용의 고객 발화 929개를 같은 seed로 다시 합성해, 그대로(깨끗한 음성)와 τ-Voice의 Realistic 열화(배경 소음 15 dB ±3, 분당 1회 돌발 소음, 발화 20%에 먹먹함, 8 kHz μ-law, 평균 2% 프레임 손실)를 거친 것(열화한 음성)을 같은 인식기(turbo)로 받아 적었다. LLM은 쓰지 않았다. 같은 소리의 두 조건을 짝지었으므로 차이는 열화의 몫이다.

| 929발화 (과제 24개) | 깨끗한 음성 | 열화한 음성 | 차이 [95% 구간] |
|---|---|---|---|
| 글자 오류율 | 4.40% | 6.39% | +2.00%p [+1.11, +3.25] |
| 이름 정확 생존 (V4 본인 확인의 기준) | 60.0% (99/165) | 50.9% (84/165) | −9.1%p [−18.7, +0.0] |
| 주문·접수 번호 생존 | 63.5% (80/126) | 58.7% (74/126) | −4.8%p [−9.2, −1.3] |

- 깨끗한 쪽은 9단계 기록을 다시 냈다 (받아쓰기가 글자까지 같은 발화 99.7%)
- 이름 생존은 받아쓰기 한 번으로 이름이 맞는 발화의 비율이다. 에이전트는 이름이 맞지 않으면 다시 묻기 때문에, 본인 확인 성공률(9단계 개발용 80.2%)이 얼마나 내려가는지는 이 표로 알 수 없다. 그것을 재는 B단계(에피소드)는 열지 않았다
- 한 화자의 합성 음성에 생성 소음을 얹은 것이라 실제 통화 성능이 아니다 ([docs/experiments.md](docs/experiments.md) 11단계 결과와 읽는 법)

## 한계

- 과제, 규정, 에이전트를 같은 쪽이 만들었다. 실제 고객 대화가 아니고, 고객 역할은 LLM 시뮬레이터다. 시뮬레이터는 한 번 점검해서 고쳤지만(첫 점검에서 20개 중 7개에 결과를 바꿀 만한 잘못이 있었다) 잡음은 남아 있다 (8단계에서 다시 읽은 60개 중 13개)
- 과제 수가 적다 (개발용 24개, 시험용 40개). 차이의 95% 구간 폭이 ±10%p를 넘으므로 그보다 작은 차이는 구분하지 못한다. 같은 설정을 두 번 쟀을 때 pass^1은 20.8%와 19.8%로 같았지만 pass^4는 12.5%와 4.2%로 달랐다
- 기준 모델(7B)의 성공률이 바닥에 가깝다. 나빠질 여지가 작아서 악화는 눌려 보이고, 개선 후보들이 실패한 이유가 후보에 있는지 모델에 있는지 가르기 어렵다
- 한 대의 PC에서 GPU 한 장으로 쟀고, 다른 프로그램이 GPU를 함께 쓴 실행이 있다. 그런 실행의 시간 수치는 쓰지 않았고 어느 실행인지는 `docs/experiments.md`에 적었다. 성공 여부에는 영향이 없다
- 음성 채널은 합성 음성으로 쟀다. 또박또박하고 잡음이 없어 실제 통화보다 쉬운 조건이다. 실제 마이크로 해 보면 다른 오류가 나온다 (전화번호가 숫자가 아니라 한글로 적히고, 말 없는 녹음에서 없는 문장이 나온다)
- 현실 조건 차이: 같은 합성 음성에 전화 통화 조건(생성 소음, 8 kHz μ-law, 프레임 손실)을 얹으면 글자 오류율이 4.40%에서 6.39%로, 이름 정확 생존이 60.0%에서 50.9%로 나빠진다 (11단계, 인식만). 사람 목소리·실제 소음·실제 코덱으로는 재지 않았고, 이 조건에서 에이전트의 성공률도 재지 않았다
- 서비스는 시연 수준이다: 프로세스 하나, 관리자 인증은 공유 토큰, 요청 빈도 제한 없음. `docs/service.md`의 "하지 않은 것"

## 다시 재는 방법

```bash
ollama pull qwen2.5:7b-instruct
uv run python -m support_agent.run --tasks dev --trials 4 --label again          # 기준 (35분쯤, RTX 2080 Ti)
uv run python -m support_agent.analyze table outputs/runs/<run_id>
uv run python -m support_agent.analyze compare reports/<기준 실행> outputs/runs/<run_id>
```

- 발화와 도구 호출의 seed는 (기본 seed, 과제, 시도, 역할, 호출 순번)에서 나오므로 같은 명령은 같은 seed로 돈다. 그래도 GPU 연산 순서 때문에 에피소드가 글자 단위로 같지는 않다
- 실행마다 `manifest.json`에 커밋, 설정, 모델 digest, Ollama 버전, 프롬프트·과제·seed DB의 해시가 남는다. 두 실행을 짝지어도 되는지는 `analyze same-setup <실행 A> <실행 B>`가 확인한다
- 이 저장소의 수치는 모두 `reports/`의 기록에서 다시 계산된다: `analyze table`, `compare`, `voice`, `claims`. 모델 없이 된다
- 새 클론에서 모델 없이 확인한 것(설치, 린트·테스트, Compose 빌드와 기동, 모델 대역으로 상담 하나, 기록에서 수치 다시 계산)과 확인하지 않은 것(실제 모델로 다시 재기)은 [docs/plan.md](docs/plan.md)의 "새 클론 확인"에 있다 (2026-10-02)
- 후보별 옵션: `--policy P1`, `--reasoning R1|R2`(R2는 10단계의 쓰기 전 고객 확인), `--guard G1|G2`, `--rescue F1`, `--claims C1|C2`, `--model qwen2.5:14b-instruct --user-on-cpu --num-ctx 8192`, `--voice V1|V2|V4`(`uv sync --group voice` 필요. V4는 9단계의 발신 번호 본인 확인). 시험용 과제는 `--tasks test --allow-test`이고 단계마다 한 번만 잰다
- 8단계 옵션: `--model qwen3:4b-instruct-2507-q4_K_M --think off --num-ctx 12288 --user-num-ctx 12288` (`--think`는 에이전트에만, `--user-num-ctx`는 시뮬레이터의 컨텍스트, `--user-num-gpu N`은 시뮬레이터 층 N개만 GPU에). 에이전트와 시뮬레이터가 같은 모델이면 실행기 옵션이 같아야 한다 (다르면 Ollama가 턴마다 모델을 다시 읽으므로 시작하지 않는다). 표는 `analyze smoke`, `select`, `verdict`, 시뮬레이터 점검은 `analyze blind`·`unblind`

## 실행

Python 3.11과 [uv](https://docs.astral.sh/uv/)가 필요하다. 테스트는 GPU와 모델 없이 돈다.

```bash
uv sync
uv run pytest
uv run ruff check .
```

실제 모델로 돌리려면 [Ollama](https://ollama.com/)와 모델이 필요하다.

```bash
ollama pull qwen2.5:7b-instruct
uv run python -m support_agent.run --tasks smoke --trials 1
```

- 결과는 `outputs/runs/<run_id>/`에 남는다: `manifest.json`(설정, 커밋, 모델 digest, 프롬프트·과제 해시), `episodes.jsonl`(대화 전체, 도구 호출, DB 변경분, 판정), `summary.json`
- `--policy P1`은 코드로 검증할 수 있는 규정을 도구 안에서도 막는다. `--reasoning R1`은 think 도구를 보여 준다
- GPU 메모리를 다른 작업이 쓰고 있으면 시작하지 않는다 (`--force`로 무시)
- Ollama 주소는 `OLLAMA_BASE_URL`로 바꾼다 (기본 `http://127.0.0.1:11434`)

### 서비스와 MCP 서버

```bash
ollama pull qwen3.5:4b
docker compose up --build        # 채팅 http://127.0.0.1:8062, 관리 화면 /admin (기본 토큰 local-admin)
```

- 에이전트 모델은 `qwen3.5:4b`(비사고 모드, Ollama 0.35.1에서 쟀다)다. 2026-10-04까지는 qwen2.5 7B였다. 바꾼 이유와 알려진 위험(과제가 요구하지 않은 쓰기 6 → 13건)은 위 8단계 결과에 있다. 이전 모델은 `.env`에 `MODEL=qwen2.5:7b-instruct`
- 평가와 같은 에이전트 루프와 도구가 PostgreSQL 위에서 돈다. 도구가 규정을 막고, 환불액 10만 원 이상인 취소·반품(반품은 같은 주문에 접수된 반품과의 합계)은 관리 화면에서 사람이 승인해야 실행된다. 고객 메시지, LLM 호출, 도구 호출, 승인 결정은 감사 로그에 남는다
- Docker 없이: `uv run uvicorn support_agent.service.app:create_app --factory --port 8062` (SQLite 파일)
- MCP 서버: `uv run python -m support_agent.mcp_server` (읽기 도구만), `--scope write`(쓰기 포함), `--http`(토큰 필요). MCP로 호출해도 규정 검사, 사람 승인, 감사 로그를 똑같이 지난다

## 구조

```
src/support_agent/
  db.py, seed.py      가상 쇼핑몰 DB(테이블 13개)와 seed 고정 데이터
  toolkit.py          도구 정의와 단일 실행 경로 execute()
  tools.py, rules.py  도구 14개와 규정 계산
  prompts/            규정 문서, 에이전트 지침, 시뮬레이터 지침
  chat.py, ollama.py  제공자 중립 메시지 타입과 Ollama 연결
  agent.py            에이전트 루프 (프레임워크 없이 직접 구현)
  claims.py           "끝났습니다"에 도구 결과의 근거가 있는지 (완료 주장 가드)
  user_sim.py         사용자 시뮬레이터
  judge.py            정답 재실행, 판정, 과제 검증, pass^k
  episode.py, run.py  에피소드 실행과 CLI
  analyze.py          기록에서 표와 짝지은 부트스트랩 구간을 다시 계산
  service/            FastAPI 채팅, 감사 로그, 승인 대기열, Alembic 마이그레이션, 화면
  mcp_server.py       도구 등록부를 MCP 서버로
  voice/              말로 풀어 쓰기, 음성 합성·인식 래퍼, 음성 채널, 채널 지표 (선택 의존성 `voice`)
tasks/                과제 파일 (YAML): smoke 5, dev 24, test 40
reports/              공식 측정의 에피소드 기록 (대화, 도구 호출, DB 변경분, 판정)
```

- 에이전트 루프, 정답 재실행, 서비스, MCP 서버가 모두 같은 `execute()`를 지난다: 인자 검증 → DB 세션 하나 → commit 또는 rollback
- 도구·seed·판정 코드는 현재 시각, uuid, 난수를 쓰지 않는다. 시각은 과제에 적힌 고정 시각뿐이라 "수령 후 7일" 같은 규정이 언제 돌려도 같게 판정된다
- 평가는 에피소드마다 메모리 SQLite 복사본을 쓰고, 서비스는 같은 테이블 정의와 도구 코드를 PostgreSQL 위에서 돌린다
